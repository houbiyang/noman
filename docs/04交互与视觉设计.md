## 2. 业务流程与操作反馈

### 2.1 全局页面结构与导航

系统在同一电脑提供红方操作员、蓝方操作员和中立主持人的独立视图，可分别在不同窗口打开。三种视图共用全屏 Unity 三维地图、总览/单位跟随模式、顶部悬浮 HUD 和周边按钮；详细信息按需打开浮层、底部时间线或右侧抽屉，可见内容和操作能力按角色区分。

| 区域 | 内容 | 行为 |
| --- | --- | --- |
| 顶部状态区 | 当前角色、对局任务、对局状态、“仿真第 N／60 分钟”、剩余仿真分钟、最近本机保存状态；主持人并列看红蓝任务节点，操作员只看本方节点 | 同时解释“每次推进 1 分钟”；保存时间与仿真时间分别命名；不通过比分卡泄露对方进度 |
| 地图主区域 | Unity 固定虚构三维地形外观、区域、道路、设施、任务点、撤离点、红蓝部署区、当前角色可见单位及行进交战状态 | 准备阶段可在本方部署区放置一个兵营并配置部队；运行阶段地图承载位置与变化，高写实纹理不能盖过标签与任务标记 |
| 按需状态浮层 | 待确认建议入口、任务节点、本方 3 个初始单位及新增单位、资源额度、AI 总指挥摘要及不确定信息；主持人可看双方 | 待处理事项置顶；单位按类型分组与局部滚动，选中可见对象时展示详情；不展示当前角色无权获知的数据 |
| 按需底部时间线 | 当前步附近的事件、建议、人工处理与任务节点 | 对局中按权限显示；复盘时联动沙盘跳转到选中步 |
| 上下文抽屉 | 待确认建议或主持人事件控制 | 从右侧展开，保留地图可见；关闭后回到同一对局上下文 |
| 全局反馈 | 对局推进、事件触发、自动保存、AI 服务及历史读取状态 | 处理中、成功、失败均有文字，不能以旧数据冒充新结果 |

**默认入口为实时沙盘**。尚无对局时，显示空地图和“未开始”；主持人看到“创建对局”与“历史存档”，红蓝操作员看到“等待主持人创建对局”。主持人创建后，红蓝进入各自的准备与部署视图；双方准备完成才由主持人开局。历史入口区分未结束的可继续存档与已结束的只读复盘。对局准备、决策处理和事件控制留在对应上下文中，避免出现与角色权限不符的空页面。

红蓝对局中看到本方单位与私有状态、公开的天气与公共区域状态，以及本方已发现的对方单位和相关交战信息；未发现单位与对方私有状态保持不可见。主持人看到双方全局，但没有代替任一操作员选择部队或确认、修改、驳回建议的入口。赛后复盘才向三个角色展示双方完整记录。前端隐藏不代替数据权限校验。

### 2.2 实时沙盘

#### 2.2.1 页面区域与显示顺序

地图是主区域，按需状态浮层按“待确认建议（有待办时）→ 任务与节点 → 异常单位 → 本方单位分组 → 资源指令预算 → 总指挥局势摘要 → 不确定信息”的顺序组织。没有待确认建议时，首位回到任务与节点；已处理建议留在时间线和详情入口，不持续占据主位。底部时间线打开后按仿真分钟展示该角色可见的事件与处理记录。顶部状态区持续显示“未开始、部署中、运行中、已暂停、等待人工确认、已结束”之一；“交战中”作为单位状态出现。

顶部战场状态条把“当前任务、已完成节点数、仿真第 N／60 分钟、剩余分钟、暂停或待确认状态”组织成一眼可读的摘要。剩余分钟按任务截止时间减去当前仿真分钟展示；对局结束后改为结束时间和结果，不继续倒计时。主持人可并排查看红蓝两方的任务节点数与待处理状态；红蓝操作员只显示本方任务进度，对方信息仅在规则允许公开时显示。顶部摘要与右侧详细节点、底部时间线取自同一仿真状态，不采用独立的演示数字。

由于本项目固定地图本身已占据主视图，首轮不增设重复的小地图。地图默认突出当前任务点、选中单位、已确认路线与正在生效的公开事件；区域和设施名称保持可辨，次要说明收进对象详情。临近任务截止或事件恢复时，提高相应标记和文字提示的显著程度，结束后恢复常态；不靠持续闪烁表达结果。

地图对象采用设计系统规格中的阵营色、角色形状和中文标签。红方、蓝方各有侦察无人机、陆兵和保障 3 个初始单位，准备阶段可新增多个单位；AI 总指挥作为建议来源展示在状态浮层，不画作地图单位。地图上的区域、道路、设施、任务点、撤离点与双方部署区均有可辨标记，不能仅靠地形插画推断。

选中当前角色可见的单位或任务点时，对象详情浮层展示对应名称、状态、有效时间与相关任务节点，并给出定位到该对象的入口；再次选中其他对象时只更新该对象详情，不把前一对象的状态带入当前对象。单位数量增加时，先显示“侦察无人机／陆兵／保障”分组及组内在线、待命、异常数量，再展开到单个单位；不能用固定三槽位裁掉新增单位。对象详情是当前沙盘状态的查看入口，不改变对局规则。信息过期、通信中断或来源缺失时显示“不确定”和最后有效步数，不显示伪实时位置。

#### 2.2.2 红蓝操作员视图

红蓝两方共用同一布局，但阵营标识、单位列表和可见事件按本方切换。顶部没有暂停、继续、单步推进和事件注入操作。存在本方关键建议时，右侧待确认抽屉展开；另一方的私有建议和单位故障不在本方地图、状态浮层或时间线出现。

本方状态浮层至少显示当前任务模板、三个节点的完成状态、截止仿真第 60 分钟、本方已执行与剩余资源使用指令，以及全部已部署单位的可用性。故障暂停剩余步数、通信报告的不确定性、交战状态和天气造成的本方进度延迟分别显示原因，不合并为笼统的“异常”。

#### 2.2.3 中立主持人视图

主持人视图在同一地图上显示双方完整状态，并提供“创建对局”“暂停／继续”“单步推进”“事件控制”“手动存档”“退出对局”等与当前状态相符的入口。主持人可以核对双方任务与事件，不出现“确认红方建议”或“确认蓝方建议”按钮。系统因任一方建议待处理而暂停时，顶部标明待处理方；主持人无法绕过该状态继续推进，仍可按保存规则存档并退出。

#### 2.2.4 行进、发现与交战反馈

已确认的任务由 AI 总指挥与部队智能体自主执行。主持人每推进一次仿真步，地图根据规则产生的位置与状态变化展示单位行进；单位卡显示当前位置、当前任务和状态，时间线记录关键变化。地图上的移动动效用于说明上一仿真状态到当前状态的变化，不产生额外的仿真时间或行动结果。

当统一规则判定对方单位已被本方发现时，操作员地图才显示该对方单位；失去发现时，不继续以实时单位样式显示旧位置。交战发生时，当前角色有权看到的参与单位、地图局部标记、单位卡和时间线共同显示“交战中”；结束后显示实际状态变化及可追溯结果。主持人可看双方完整过程，赛后复盘开放双方记录。发现需满足来源可用、范围、无规则阻挡与共享条件，失视当步停止实时更新；首版陆兵间抽象对抗按资格与同一步统一结算。具体数值、公式、持续与中断技术细节待设计，本文件不预填参数。

操作员不直接逐次操控单位移动或交战。需要调整行动时，仍通过本方 AI 总指挥方案与既有人工确认流程处理；任务目标与比分由统一仿真规则决定。

### 2.3 对局准备与开始

主持人在未开始的沙盘点击“创建对局”，打开占点测试准备区，按“规则版本与参数 → A/B/C 点位及通路检查 → 预设事件 → 双方准备 → 开始前检查”排列。双方共用三个控制区，资源显示单位能源、补给和库存，不显示旧 20 条计费指令预算。

主持人创建对局后，两方操作员分别进入本方**兵营放置与部队配置**状态。操作顺序为选择兵营 → 在本方部署区预览完整占地、地面出入口和无人机停靠点 → 确认合法位置 → 在兵营内配置 3 个初始单位及新增部队。兵种卡显示名称、类型、已配置数量与选择状态；配置不扣建造资源、无单位数量上限。越界、重叠、缺少道路接入或停靠点不可用时说明原因。开始后关闭兵营移动和新增配置，部队按已确认方案从对应出发点出现；待命数量保留在兵营列表，不把所有待命图标堆在地图。坐标、占地尺寸、接入阈值及具体属性数值待设计。

“布置任务”指操作员在主持人已配置的任务目标范围内，为本方已部署单位确定分工与优先级；不在此入口修改任务模板、目标、截止时间或评分规则。两方分别提交“准备完成”后，主持人看到双方准备状态，但对方部队组合在对局开始前仍按角色权限隔离。主持人不能代任一方放置兵营、配置部队或修改任务分工。

开始前检查规则版本、公共点几何和道路可达、同一兵种目录与部署政策、双方准备状态。当前地图非对称，尚未验证正式平衡，不显示“公平已通过”。几何或规则缺项时阻止开局，不猜测补值；开始后关闭兵营移动及新增配置，进入首次方案确认。

对局准备区的具体场景字段、地图坐标、部署校验和事件脚本参数由后续场景设计确定。本阶段 UI 不新增多地图、真实地图导入或实体设备配置入口。

### 2.4 AI 建议与人工确认

#### 2.4.1 待确认抽屉

首次分配、单位改派、进攻／防守目标点变化或资源额度重大变化时，系统暂停，所属方出现待确认建议入口。抽屉标明本方、相关单位及仿真步；主持人只看到等待状态和推进受阻原因，不能代确认。

抽屉依次显示分工和目标点、来源与有效报告、路线与完整占领步估时、能源／补给影响、不确定项，以及确认／修改／驳回。公开争夺状态不自动升级为已发现敌方单位；失联和过期报告标为不确定。

操作员点击“确认建议”后，页面显示处理中，再将经确认的任务写入时间线；失败时保留待确认卡和原因。点击“驳回建议”后记录原建议、驳回动作和仿真时间，保持该建议未执行。驳回后的重新建议时机由智能体流程确定，页面不虚构下一条已存在建议。

#### 2.4.2 修改与校验

“修改建议”在同一抽屉内展开可编辑区，仅包含本方已部署虚拟单位分工、任务优先级和资源额度。提交前展示修改前后内容及资源变化，不允许编辑对方单位、事件规则、地图或评分规则；开局后的建议抽屉不提供新增部队放置。

提交时检查本方单位归属、可用性、主动作、路线、实际行动资源及第 60 步截止。错误定位到字段并保留草稿；成功保存建议与人工修改记录。任一方待确认时主持人不可推进。

#### 2.4.3 AI 服务不可用

若 AI 建议服务不可用，所属方待确认区域明确显示“建议服务不可用”，不出现伪造的建议、依据或预期影响。首次任务分配保持待处理状态，不能悄悄按默认方案推进；主持人视图只看到该方等待状态。仿真规则、计分和已保存复盘的离线可用性仍按 PRD 保持。

### 2.5 主持人事件控制

主持人点击“事件控制”后，从右侧打开抽屉，地图及当前步数仍可见。抽屉依次展示事件类型、影响方或对象、触发步数、固定效果、可见范围与“预览影响”。手动触发前必须先预览，预览中再次标出是否为双方公开事件及受影响状态；点击“确认触发”后才进入执行状态。取消预览不改变沙盘。

| 事件类型 | 抽屉预览中的固定效果 | 触发后的可见反馈 |
| --- | --- | --- |
| 设备故障 | 指定单位暂停 5 步 | 本方与主持人看到受影响单位、开始／恢复步数；另一方不见私有故障 |
| 通信中断 | 受影响报告标为未知 5 步 | 本方报告显示“不确定”和最后有效步数，旧报告不作为实时事实 |
| 天气变化 | 受影响任务进度延迟 5 步 | 双方看到天气事件，受影响方看到本方进度延迟说明 |
| 任务变化 | 替换目标直到本局结束 | 本方看到新目标与待确认建议；旧进度留在时间线，新目标从 0 节点开始 |

预设脚本与手动触发使用相同名称、固定效果和时间线样式，并注明触发来源。事件触发中避免重复提交；失败时显示原因并保留抽屉输入，不生成“已触发”记录。成功时显示生效步数、影响对象和恢复条件。注入事件本身不直接产生安全扣分；若后来发生独立的单位或设施失效，另以损失事件和计分变化展示。

### 2.6 时间推进、自动保存与结束

#### 2.6.1 推进控制

只有主持人可操作暂停、继续与单步推进。顶部主要显示“仿真第 N／60 分钟”，旁边说明“每次推进 1 分钟”；单步推进一次只进入下一仿真步。推进处理中禁用重复操作，成功后地图上的位置、发现与交战状态、右侧单位卡和底部时间线同时更新到同一步。待人工确认时系统自动暂停，主持人看到“等待红方／蓝方确认，暂不能推进”。

主局按 CQ-05 判定连续全控、胜利分阈值或第 60 步截止。结束后推进与事件触发入口不可执行，结果页展示冻结胜利分、胜负及结束原因。页面把仿真步数与本机实际保存时间分开显示。

#### 2.6.2 本机自动保存

每次成功推进一步、人工处理建议或事件触发后，系统自动保存该局的状态与记录；兵营位置及连接点、部队配置与待命状态在对局开始时一并保存，对局结束时再保存最终结果。顶部显示“正在保存”“已保存及最近本机保存时间”或“保存失败”。保存失败时不能显示为“已保存”，也不能把尚未持久化的过程列为可重开的完整复盘；当前窗口保留可恢复的内容并提供重试反馈。保存格式与故障恢复细节在技术设计中确定。

自动保存不改变红蓝信息边界。进行中的历史记录即使存在于本机，也不能通过另一方视图提前查看其私有信息；赛后才开放双方完整复盘。

#### 2.6.3 手动存档、退出与读档

主持人在对局中点击“手动存档”后，界面显示当前对局、任务模板和仿真步，并提供创建可区分存档的操作。手动存档成功后显示本机保存时间；失败时保留当前对局并显示原因。手动存档可以有多个，具体槽位数量、命名和覆盖规则留后续设计。红蓝窗口不出现整局存档或读档按钮。

主持人点击应用内“退出对局”时，先暂停整局，再弹出三个选项：“存档退出”“不存档退出”“取消”。弹窗说明当前仿真步和最近一次成功自动存档的仿真步。“存档退出”在手动存档成功后离开对局，失败时保持弹窗和对局；“不存档退出”不创建新的手动存档，但保留最近自动存档供下次恢复；“取消”关闭弹窗并返回已暂停的对局。退出后红蓝窗口显示本局已暂停，等待主持人继续。

主持人从历史存档点击“继续游戏”后，读取整局状态，使红蓝回到同一仿真步，并恢复开局部队组合、单位位置与状态、任务、资源、发现与交战状态、事件、建议待确认状态和时间线。读档成功后仍显示“已暂停”，由主持人决定继续或单步推进；读取失败不改变当前有效对局。直接关闭浏览器窗口时不依赖自定义退出弹窗，重新进入后从最近成功写入的自动存档恢复。

### 2.7 结果、历史对局与复盘

结果页展示双方胜利分、结束步、结束原因、各点控制轨迹和计分事件。开局单位数、能源、补给及实际损失作为统计单列，不折算胜利分。同一步达到阈值或时限时同分显示“平局”，全控胜利按 CQ-05 单独标识。

“历史存档／对局”入口分为未结束存档和已结束记录。未结束存档显示自动或手动来源、任务模板、保存步数和本机保存时间；主持人可点“继续游戏”，红蓝只能看到恢复后的各自视图。已结束记录显示任务模板、结束状态、红蓝结果和本机保存时间；三角色可点“查看复盘”进入只读详情。保存失败的记录不能伪装成可继续存档或完整复盘。查询未命中与读取失败使用不同文案；读取失败提供重试，不显示空结果冒充查询成功。

复盘使用与实时沙盘同位置的底部横向时间轴。事件标记至少区分任务节点、条件注入、发现与交战、AI 建议、人工处理和计分变化；选中标记时先显示一句事件摘要，再可查看完整依据。用户拖动时间轴或点击前后步，地图、双方单位位置与状态、发现与交战、任务节点、事件、AI 建议、人工处理和得分变化同步切换到所选仿真步。第 0 步能查看双方兵营位置、连接点与部队配置记录；当前步有明显标记。复盘不提供推进仿真或注入事件入口。对局结束后红方、蓝方和主持人均可查看双方完整记录；旧任务目标和已达节点仍可在任务变化前的时间点查看。

| 操作或状态 | 处理中／等待 | 成功 | 失败或不可用 |
| --- | --- | --- | --- |
| 创建对局 | 检查任务模板、双方对称条件和场景配置 | 回到实时沙盘并显示当前步 | 列出不满足的条件，留在准备区 |
| 放置兵营并配置部队 | 地图预览建筑占地及连接点，兵种卡显示已配置数量 | 兵营合法落位，配置写入兵营列表且不扣建造资源；开始后从对应出发点出发 | 保留选择，说明越界、占用或连接失败原因 |
| 提交准备状态 | 展示本方任务分工、优先级和部署单位摘要 | 主持人看到本方“准备完成”，双方准备完成后可开局 | 说明尚未完成的放置或任务配置，不替玩家自动完成 |
| 处理 AI 建议 | 待确认卡显示所属方、依据与资源变化；提交中防重复 | 时间线记录确认、修改或驳回结果 | 保留卡片和输入，显示校验或服务错误 |

| 事件触发 | 先预览固定效果和可见范围；触发中防重复 | 时间线记录来源、生效与恢复信息 | 保留抽屉输入，不生成已触发记录 |

| 自动保存 | 顶部显示“正在保存” | 显示最近本机保存时间 | 显示“保存失败”，不声称已可重开 |
| 手动存档 | 显示当前仿真步与保存中状态 | 生成可区分的存档并显示保存时间 | 保持当前对局，显示失败原因，不生成可继续条目 |

### 2.9 部署、探索与保障的交互要求

本节细化 [02 仿真规则与参数](02仿真规则与参数.md) 中已有规则的显示与操作反馈。

1. 兵营预览检查完整占地和全部连接点；开始前检查每方一个合法兵营、部队配置、任务及场景条件。首次方案未确认时不能推进首步。
2. 兵营详情显示本方配置、待命与已出发数量、连接点及补给功能；发现对方建筑不展示其内部部队或库存。
3. 编队卡显示成员分工、节点能力要求及正常执行、能力受限、等待协作、任务受阻或完成；异常提示关联具体成员与节点。
4. 三态探索使用未侦察暗罩、已侦察淡雾、当前可见清晰区；最后发现标记带仿真时间，不冒充当前单位。列表、摘要及 AI 输入执行相同权限。
5. 无人机详情关联观察来源、能源及当前航线；陆兵详情关联补给与当前主动作；保障详情关联库存、服务对象或唯一持有对象。未确定数值显示未配置，不能伪造参数。
6. 航线失败明确标出越界、禁行线段、单位状态、能源或任务条件等原因。选中单位显示当前路线，查看方案时才展开候选及依据。暗区不自动标禁飞，天气按原有 5 步延迟展示。
7. 补给处理中显示服务双方及占用步；同一对象不重复服务。操作与存档恢复保留对象唯一持有关系，保存状态涵盖兵营、编队、路线、资源、探索及报告。

### 2.10 路线、交战与失效的交互要求

- 兵营保持固定功能建筑，首版不提供兵营耐久、受击或摧毁获胜反馈；本方内部配置与库存继续按角色隔离。
- 候选方案显示可执行、信息待核验或不可执行及其原因；比较完整预计完成时间、资源变化和未知项，按时优先与节约优先可辨。候选展示数量尚未单独锁定，不隐含新的部队上限。
- 地图、列表、摘要及 AI 解释同源执行视野权限。失去全部有效来源当步将对方实时标记改为带时间的历史记录；重新发现后更新，通信中断不展示伪实时数据。
- 对抗记录仅允许本版资格内对象；核对阵营、信息、作用范围、状态、动作占用及方案权限。同一步结果统一展示，不由动画播放或红蓝处理先后决定。
- 耐久为零后显示失去任务能力并停止动作，安全事件唯一计数；临时故障与资源不足使用各自原因，结果页继续按任务、资源、安全结算。
- 验收以配套规则 RULE-13 至 RULE-21 为依据，覆盖路径中途事件与存档恢复。具体数值和技术算法仍待设计，不以占位演示结果作为通过证据。

### 2.11 数据、证据与恢复反馈

1. 三角色界面从对应角色状态获取数据，页面隐藏不替代服务端信息隔离；动画、模型文本和检索结果不自行结算游戏状态。
2. 建议抽屉的依据区关联资料名称、版本、原文位置和当时有效时间；解析失败、证据不足、模型不可用或方案过期分别提示，不生成伪引用和伪建议。
3. 已确认方案的采用结果与保存状态以服务端实际结果更新；重复提交、读档和工作流恢复不重复执行或扣费。旧分支或旧版本异步结果不能覆盖当前界面。
4. 页面结构延续既有流程，具体协议、字段和持久化实现按配套技术架构规格继续设计；本节不表示已接入后端或知识服务。

### 3.2 页面状态层级

页面按以下层级响应，避免多个面板同时抢夺焦点：

1. 全局状态：未开始、准备中、运行中、已暂停、等待人工确认、已结束、连接中断。
2. 页面内容：当前页面或实时沙盘主体。
3. 按需面板：单位详情、任务详情、建议、事件、存档和历史。
4. 确认弹窗：退出、保存、读档、触发事件等会改变状态的操作。
5. 全局反馈：成功、失败、处理中、结果待核对。

弹窗打开时保留地图和顶部 HUD 的背景状态，但阻止背景按钮误触。抽屉打开时地图可以继续查看，地图点选是否可用由抽屉类型决定；建议、事件和表单抽屉不允许地图点选写入新操作。

## 4. 按需面板、权限与错误

### 4.1 单位详情浮层

```text
┌──────── 当前可见单位 / 有效来源步 / 本方或观察对象 ──────────┐
│ 单位名称与 ID / 类型 / 当前任务与状态                       │
│ 本方：能源、补给或库存；敌方：仅允许的观察字段               │
│ [定位] [跟随单位：当前可见且有效时] [关闭]                   │
└────────────────────────────────────────────────────────────┘

┌──────── 单位跟随：同一对局 / 分支 / 角色 / 仿真步 ──────────┐
│ Unity 近景观察        目标名称 / 最后有效步 / 连接状态       │
│ [返回总览]           失视或失效：停止实时跟随并显示原因      │
│ 暂停/待确认提示和建议入口持续可达，不提供驾驶或射击按钮      │
└────────────────────────────────────────────────────────────┘
```

单位详情不是独立页面。右侧或近对象浮层显示单位名称、稳定编号、类型、来源时间、任务、状态、能源/补给/库存以及“跟随单位”。红蓝只查看本方详情及对已发现对象允许的观察字段；敌方库存、私有任务和内部配置不显示。主持人按权限查看双方。

### 4.2 任务详情浮层

任务详情显示任务模板、三个节点、执行者、截止步、当前进度、阻塞原因和允许的下一步。任务模板、目标、截止时间和评分规则在运行中不可从该浮层直接修改。

### 4.3 时间线展开

底部时间线从实时沙盘下方展开，占用固定高度；地图缩小可视区域但不改变 Unity 相机位置。点击记录可以查看摘要和来源；实时模式只查看当前或最近事件，复盘模式才允许跳转历史帧。

### 4.4 连接中断和错误状态

任何页面都使用同一错误区域：顶部状态显示连接中断或结果待核对，主体保留最近有效快照，操作区只保留重试、刷新状态或返回入口。错误状态不清空当前页面，不显示伪成功，不自动切换到演示数据。

草稿在同一有效上下文中关闭后保留；切角色、读档或权限失效时重新核对并清理不适用内容。关闭抽屉不自动提交、不解除人工确认阻塞。

| 已结束结果与复盘 | 可查看 | 可查看 | 可查看 |
| 跟随单位 | 当前允许观察的单位 | 当前允许观察的单位 | 当前允许观察的单位 |

按钮是否显示只属于体验层，服务端仍必须校验角色、会话、对局、分支、状态版本和对象可见性。

### 4.6 操作状态与错误反馈

| 操作 | 处理中 | 成功 | 失败或待核对 |
| --- | --- | --- | --- |
| 创建对局 | 创建中 | 进入 P-02 | 保留表单并显示原因 |
| 准备完成 | 校验中 | 显示本方已完成 | 显示兵营、连接、任务或配置错误 |
| 开始游戏 | 锁定检查中 | 进入 P-03/P-04 | 显示双方未满足条件 |
| 确认建议 | 提交中 | 写入已采用方案 | 保留建议和修改内容 |
| 触发事件 | 触发中 | 写入事件记录 | 预览失效或权限/阶段错误 |
| 单步推进 | 结算中 | 所有区域进入同一步 | 等待人工、版本冲突或结果待核对 |
| 手动存档 | 保存中 | 进入历史目录可继续 | 保留当前局，不显示保存成功 |
| 读档 | 读取中 | 恢复同一步并暂停 | 保留当前有效对局 |
| 查看复盘 | 加载历史帧 | 显示冻结画面 | 区分查询失败和读取失败 |

所有按钮在处理中防止重复提交。网络响应丢失时先查询原请求结果，再决定是否重试；重试不能直接重复推进、触发事件、扣分或采用建议。

## 5. 视觉规范

### 5.1 主题与资源原则

采用深色 HUD、地图优先的单主题布局，红蓝只表示阵营；错误、警告和未知须同时有文字与图形。三维总览采用虚构地形的写实外观，单位跟随使用同一场景中的单位表现。模型、材质、标签与特效的具体资源规格待确认。

旧浅色页面色值表及其对比度计算已删除，不再作为 Unity UI 的设计要求。具体色值、字体与间距须在选定的 UI 框架和实际画面中验证；下文数值只作待验证设计建议。相机总览/跟随操作由 Unity 规格定义，界面始终显示角色、有效仿真步、暂停或待确认状态及返回入口。

### 5.2 视觉原则

1. **局势优先**：地图承载部署、位置、行进与交战，状态浮层承载可核对的数据，时间线承载事件与决策。地形插画不能盖过单位、任务节点和暂停原因。
2. **阵营与语义分开**：红、蓝只表示阵营；错误、警告、成功使用独立的符号和文字。不能把红方标记误读为失败，也不能把蓝方标记误读为普通链接。
3. **颜色与文字并行**：设备故障、通信中断、不确定报告、待确认建议及任务结果都要有文字标签；颜色、动画或插画不能成为唯一线索。
4. **可见范围可信**：红蓝实时视图绘制本方单位、公开事件和本方已发现的对方单位；未发现的对方单位及其私有状态不显示。主持人可看双方全局；赛后复盘才向三角色展示双方完整记录。遮盖私有信息不是权限控制的替代。
5. **时间一致**：沙盘、状态浮层、建议卡和时间线都标明同一仿真步数。回放跳转时，视觉状态和对应记录一起变化。
6. **本机可读**：在 1920 × 1080 的桌面窗口中，沙盘、当前状态、开局部署、人工确认与主持人时间控制保持可见、可操作；新增单位无数量上限，列表与地图标记必须能扩展显示，具体布局在页面设计中验证。
7. **行动与结果分层**：行进方向、交战提示和任务完成反馈靠近地图对象呈现；规则结果以文字与时间线记录固定下来。动效不能自行改变仿真状态。

### 5.3 字体、数字与时间

| 层级 | 建议规格 | 用途 |
| --- | --- | --- |
| 页面标题 | 24 px / 32 px，半粗 | 实时沙盘、结果与复盘标题 |
| 区块标题 | 18 px / 26 px，半粗 | 状态浮层、事件控制、建议卡区块 |
| 正文与控件值 | 14 px / 22 px | 列表、表单、建议依据 |
| 地图标签 | 不小于 13 px / 18 px | 单位、任务点、设施名称 |
| 辅助文字 | 12 px / 18 px | 来源、最近有效步数、保存时间 |
| 胜利分 | 28 px / 36 px，半粗 | 冻结的占点累计胜利分 |

中文文字需在选定的 Unity UI 或网页外壳中验证字体、字形资源和授权。现有网页字体栈只作参考，不将 CSS 字体声明当作 Unity 字体已配置；不新增网络字体下载要求。步数、分数、资源额度和计时数字采用等宽数字特性；分数与数量右对齐，名称与说明左对齐。

- 主要时间写成“仿真第 12／60 分钟”，辅助说明“每次推进 1 分钟”；复盘或调试位置可另标“第 12 步”。保存时间另标“本机保存时间”，不与仿真时间混用。
- 占点胜利分显示精确非负整数及目标值；控制进度显示完整步数。测试值为每点每步 1 分、目标 60 分，实际以绑定规则版本为准。
- 能源、补给、库存、胜利分分别命名；占点主局不展示旧 20 条计费指令预算。兵种列表明确标“开局建造暂不消耗资源”。
- “0”表示已确定为零；“未提供”“不确定”和“建议服务不可用”分别表示缺值、信息不可信和服务故障，不以零或空白代替。

### 5.4 布局、间距与表面

建议以 4 px 为基础间距单位：标签与值相隔 4–8 px，同组信息相隔 12–16 px，不同功能区块相隔 20–24 px。当前信息浮层和卡片使用清楚的边框及少量阴影；深色沙盘用半透明信息底衬让文字从高写实地形中分离。建议卡片圆角 8 px、控件圆角 6 px、常规操作控件高度 40–44 px。以上数值为设计建议，不作为已验证的页面结果。

在 1920 × 1080 桌面基线下，地图铺满视口，HUD 和周边按钮保持可达。部队详情打开后按异常、执行中、待处理分组并局部滚动，不用三槽位裁掉成员；时间线仅在打开时占用地图前景。兵营预览、配置弹层和待确认抽屉不能挡住当前主要操作，关闭后保留视口与待办。覆盖层比例由当前原型和真实内容验证，不划出永久右栏。

窄于最低验收尺寸时允许详情面板或时间线局部滚动，不应通过缩小全部文字来容纳内容。首版不承诺移动端专用布局。固定的任务与阵营标签在缩放或滚动时应保持可定位；具体缩放功能由交互设计决定，本规格不新增地图缩放操作。

### 5.5 地图、单位与任务符号

#### 5.5.1 地图视觉层级

地图采用 Unity 三维场景，**虚构地形的高写实卫星图风格**作为总览美术参考，跟随视角使用对应场景资产：通过地貌纹理、道路、设施与区域明暗提供空间感，但不使用真实地理坐标来暗示实际区域。真实感属于视觉表现，不改变一张固定虚构地图、四类任务和统一规则的产品边界。红蓝部署区在准备阶段须可辨，对局开始后转为低干扰背景标识。

从下到上依次呈现地形插画、道路与区域、双方部署区、任务与设施、单位及已确认的行进轨迹、状态与选中信息。道路和区域边界在地形上应可辨；任务点及撤离点不能被插画纹理掩盖。强对比标签使用深色底衬或描边，确保在浅色地形和暗色地形上均能读出。大量单位聚集时可按位置聚合并标数量，选中后仍能逐个查看，不得把单位静默隐藏。

| 对象 | 建议视觉表达 | 必须保留的文字信息 |
| --- | --- | --- |
| 区域 | 半透明边界与区域编号 | 区域名称、是否为当前任务区域 |
| 道路 | 连续清晰的线条，弱于任务路线与单位 | 道路或连接关系的可辨说明 |
| 设施 | 三维设施模型与可辨标签 | 设施名称、正常或失效状态 |
| 任务点 | 带序号的菱形或圆角方形标记 | 节点名称、完成状态 |
| 撤离点 | 带中心符号的圆形标记 | “撤离点”文字和当前状态 |
| 红蓝部署区 | 各自阵营描边与半透明填充；准备阶段显示合法放置范围 | 阵营名称、“仅本方可放置”及放置校验原因 |
| 兵种列表卡 | 单位插画缩略图、名称、类型形状与选中边框 | 兵种名称、兵营内已配置数量、“开局配置暂不消耗资源” |
| 兵营 | 建筑占地预览、地面出入口及无人机停靠点标记 | 阵营、待命数量、连接点和放置校验原因 |
| 侦察无人机单位 | 三维模型配圆形识别标记 | 阵营、单位名称、可用状态 |
| 陆兵单位 | 三维模型配三角形识别标记 | 阵营、单位名称、可用状态 |
| 保障单位 | 三维模型配方形识别标记 | 阵营、单位名称、可用状态 |
| 行进中单位 | 单位原有标记加短轨迹或方向提示，随仿真步更新 | 单位名称、当前任务、当前仿真分钟 |
| 交战状态 | 局部高亮与交战标记，结束后保留状态结果 | “交战中／交战结束”、涉及的可见单位、结果及仿真分钟 |

单位模型与图标提供细节和演示氛围，外轮廓形状、阵营色、中文名称和状态标签承担实际识别。红方与蓝方即使在灰度查看或颜色感知不同时，也应能凭形状与文字辨认。主持人视图可见双方单位；红蓝操作员对局视图只绘制本方单位及本方已发现的对方单位，发现状态结束后不以实时样式继续展示旧位置。赛后复盘再按已确认权限展示双方完整记录。新增兵种的图形与颜色沿用同一语义规则，具体模型资源及属性待设计。

#### 5.5.2 变化与不确定性

- 设备故障：受影响单位旁出现故障文字和剩余 5 步状态；红蓝另一方不见其私有故障。
- 通信中断：报告来源区域显示“不确定”及最后有效步数，地图不以旧位置或旧状态冒充当前信息。
- 天气变化：天气为双方公开事件，用独立天气标记和文字说明；受影响方的任务延迟在本方详情面板解释。
- 任务变化：新旧目标使用不同的时间线记录，旧节点保留供复盘，新目标从 0 节点显示。
- 单位失效或设施失效：安全损失使用事件标记、文字和分数变动说明；注入事件本身不直接显示为已扣安全分。
- 对方单位被发现或失去发现：地图与详情面板同步更新可见状态，时间线记录相应仿真步；未发现状态不显示实时位置。
- 交战发生：可见参与方的单位卡、地图和时间线使用同一交战状态及仿真分钟；实际失去任务能力时才按既有安全规则展示扣分。

动态变化可有短暂动效提示，但不能依赖持续闪烁传达关键信息；动效结束后状态仍需保留文字和符号。动效时长及是否启用留页面设计验证。

### 5.6 控件与状态组件

#### 5.6.1 操作层级

- **主要操作**：当前步骤只突出一个关键动作，例如准备阶段本方的“确认部署”、主持人的“开始游戏”“确认触发”，或本方操作员的“确认建议”。按钮文案使用动作加对象。
- **次要操作**：选择兵种、查看单位、查看依据、修改建议、返回沙盘、单步跳转等使用次级按钮或文字操作。不同角色只显示其有权执行的操作；频繁使用的待确认、暂停和存档状态在主界面可见。
- **拒绝或退出**：驳回建议、取消事件触发需明确作用对象；对未执行动作不写入已成功的时间线。
- **禁用与不可用**：需要说明原因，如“等待红方确认，暂不能推进”或“建议服务不可用”，不能只呈现灰色按钮。

#### 5.6.2 待确认卡

待确认卡固定使用“所属方与提出步数 → 建议内容 → 依据及来源 → 预期影响 → 拟新增资源 → 不确定项 → 处理操作”的阅读顺序。确认、修改和驳回均应让操作员知道将影响哪一方、哪几个虚拟单位。修改区只出现本方单位分工、优先级和资源额度字段；提交失败时在字段旁给出原因，顶部提供可定位的错误汇总。主持人视图只显示“待某方处理”，不显示代确认按钮。

#### 5.6.3 事件控制卡

主持人视图的事件控制卡依次显示事件类型、影响方或对象、触发步数、固定效果和可见范围。手动触发前展示预览，确认后才改变沙盘状态。脚本事件与手动事件使用相同的名称和视觉标识，并在时间线区分“脚本触发”与“主持人触发”。红蓝视图只接收允许公开或属于本方的结果。

#### 5.6.4 通用状态标签

| 状态 | 建议表达 |
| --- | --- |
| 未开始 | 中性文字“未开始”，主持人可见创建入口 |
| 部署中 | “兵营放置／部队配置”、本方兵营占地和部署区高亮；主持人查看双方准备状态 |
| 放置不合法 | 原位置保持不变，显示“超出本方部署区”或对应校验原因 |
| 运行中 | 文字“运行中”与当前仿真步数 |
| 行进中 | 单位旁显示任务方向或短轨迹，详情面板写明“行进中” |
| 交战中 | 局部交战标记与文字“交战中”，不依赖动画或阵营色 |
| 对方单位未发现 | 不显示对方实时单位标记或位置数据 |
| 已暂停 | 文字“已暂停”及原因 |
| 等待人工确认 | 警示标签“等待红方／蓝方确认”，本方显示待确认卡 |
| 信息不确定 | 灰色问号形状、文字“不确定”、来源与最后有效步数 |
| 设备故障 | 警示形状、文字“设备故障”、剩余步数 |
| 已结束 | 中性或成功状态标签，另显示实际胜负 |
| 保存失败 | 错误图形和“保存失败”，不显示“可重开复盘” |
| 建议服务不可用 | 文字“建议服务不可用”，不生成伪建议 |

同一状态在地图、详情面板、时间线和复盘中使用同名标签。阵营色不代替状态色；红方“已完成”仍要有“已完成”文字，蓝方“失败”仍要有“失败”文字。

### 5.7 分数、时间线与复盘图形

结果页采用双方胜利分、目标值、结束原因与占点轨迹。红蓝使用相同尺度，额外列出资源和损失统计。阈值或时限同分显示“平局”；连续全控获胜显示该原因及连续步记录，不靠颜色推断胜负。

时间线以仿真步数排序。事件、AI 建议、人工处理、任务节点及得分变化使用不同图形或前缀，但名称与状态标签保持一致。复盘拖动时间轴或单步跳转时，沙盘和详情面板同步到对应步；当前选中步有明确标记，不能同时显示另一时间点的分数或单位状态。旧目标与新目标的记录分开呈现，以解释任务变化后从 0 节点重新计分的原因。

分数条在 0 分或满分时仍展示精确数字；图形不代替规则说明。任务成功 100 分，未成功按已达节点得 0、20、40 或 60 分；资源每条已执行指令扣 5 分，安全每次独立失效扣 20 分，均不低于 0。具体分数和时间线以保存的对局记录为准，不把演示占位数据展示为真实结果。

### 5.8 可读性与视觉验收

1. 在 1920 × 1080 桌面窗口中检查沙盘、3 个初始单位及新增单位列表、当前仿真分钟、关键建议、主持人时间控制和事件入口是否可读且可达；另用待设计的多单位样例检查聚合与局部滚动。
2. 用四类任务各完成一次地图检查：三个节点、目标、设施与撤离点应能在高写实地形上定位；插画纹理不能掩盖任务标记。
3. 分别在浅色地形、暗色地形、地图遮罩及白色卡片上检查红蓝阵营标签、主要文字、警示与焦点轮廓。颜色对比需结合实际叠图和透明度以渲染结果核验。
4. 在不依靠颜色的情况下，检查红蓝阵营、三类初始单位、部署区、行进与交战、任务节点、故障、未知、待确认、成功与失败是否仍可区分。
5. 用键盘依次聚焦主持人时间控制、事件控制及操作员的确认卡。焦点必须可见，校验失败后可定位并继续修改字段。
6. 检查对局进行中红蓝视图不泄露对方私有状态；赛后复盘三角色可查看双方完整记录。视觉遮挡不能替代数据可见范围校验。
7. 检查保存失败、AI 建议服务不可用及报告过期时的文字反馈，不能以空图标、旧建议或旧报告冒充有效信息。
8. 检查兵营占地、地面及空中连接点、合法放置、越界拒绝与部队配置；兵营待命数与已出发数可核对，开局后不再显示放置或新增配置操作。
9. 检查已发现的对方单位与交战反馈在地图、详情面板、时间线和复盘中的一致性；未发现单位不得以实时标记或旧坐标泄露位置。

本节是视觉验收清单，尚不是已完成的页面测试。具体屏幕截图、对比值、键盘流程和不同地形背景下的可读性，需要在原型或实现页面中核验。

### 5.9 部署、探索与保障符号

行为依据为 `02仿真规则与参数.md`。本节仅细化已确认行为的显示，不增加新的对局规则或默认数值。

- 探索三态同时配图例与文字：未侦察暗色遮罩、已侦察当前不可见的淡雾、当前可见的清晰区域。最后发现标记与实时单位采用可区分样式并显示时间。
- 地面道路持续可辨，空中航线用独立线型并标注移动类型；常态突出已确认路线，候选仅在方案上下文展开，不用颜色暗示未判定结果。
- 兵营预览显示完整占地、地面出入口、无人机停靠点及合法性原因；地图标记与配置列表分别表达待命和已出发状态，不能遗漏待命成员。
- 编队受阻提示关联成员、缺失能力和任务节点。无人机能源、陆兵补给、保障库存使用明确名称，未配置数值不能显示为零或虚构满值。
- 红蓝独立探索数据及对方兵营内部信息不能通过标记、数量、提示或列表泄露。展示验证须使用配套规则的验收案例。

### 5.10 路线和结算的视觉反馈

1. 候选路线的可执行、信息待核验、不可执行三种状态均配文字与原因；按时优先和节约优先有明确选中状态。预计时间、资源与未知项采用完整标签，具体布局待页面验证。
2. 实时可见单位、最后发现记录与未知区域以不同样式表达；失视当步更新，不能通过提示、摘要或路线理由泄露隐藏对象。
3. 兵营保持固定功能对象，不增加耐久或摧毁获胜图形。首版陆兵间抽象对抗的状态变化取自统一结算；动画和高亮只解释已生成结果。
4. 对象资格不满足、动作互斥、临时故障、补给不足和耐久为零分别显示原因；同一次安全损失只显示对应唯一事件。具体参数和素材仍待设计与实际页面验证。

## 7. 客户端职责与输入约束

### 7.1 客户端职责

| 职责 | 数据与行为边界 |
| --- | --- |
| 会话与业务协调 | 维护当前角色、对局、分支、有效版本及操作草稿；清理过期响应与无权数据 |
| 地图与单位表现 | 绘制权限过滤后的对象、路线与探索状态；不产生业务结算 |
| 相机控制 | 三维总览、可见单位跟随与返回；失视、对象无效或分支变化时停止旧跟随 |
| HUD 与按需面板 | 时间、任务、单位、建议、事件、资源和错误反馈共用同一状态版本 |
| 准备与人工处理 | 先预览/校验，再显式提交；输入或版本变化使旧预览失效 |
| 保存与复盘 | 失败不显示成功，历史只读；跳转清理旧动画、特效与跟随对象 |

原 Vue 文件树、props/emits 清单、SVG 渲染及强制 History API 路由方案已退出目标架构。现有 Vue 原型保留作交互参考；业务面板是否继续采用网页待 D-15 确认。稳定标识、空值/未知、重复操作与只读边界继续适用，FE-COMP、FE-ARCH 用例统一保留在测试文档。

### 7.2 共用展示与输入规则

基础层只抽取跨业务区块稳定复用的状态标签、带错误提示输入、面板外壳、抽屉外壳、进度、时间与反馈。Vue/CSS 基础组件作为既有原型参考；地图与战斗画面采用 Unity，Unity UI 组件方案与字体资源需另行核对，本轮不安装依赖。

| 规则 | 组件表现 |
| --- | --- |
| 空值、零与未知 | 零明确显示为零；缺少配置显示“未配置”；报告未知显示“不确定”与最后有效时间，不用零代替 |
| 仿真时间 | 主展示为“仿真第 N／60 分钟”；需要解释时说明一步等于一分钟，保存时间独立标为本机保存时间 |
| 阵营与异常 | 红蓝代表阵营，失败、故障、待处理和未知同时使用文字与图形，不能只依靠阵营色 |
| 地图与标记 | 保持现有俯视地图、小标记、选中或悬停名称；详细字段进入面板，点选命中区不必与可见图标一样小 |
| 拖动与覆盖层 | 地图拖动不误触放置；面板操作不穿透；弹层关闭后保留可用地图视口，不能拖走 HUD |
| 演示数据 | 当前原型数据和固定建议持续显示演示标记；占位内容不混入真实任务、服务结果或存档 |
| 错误定位 | 任务格式、双方共享约束、建议字段和事件输入分别定位错误，提交失败保留可恢复内容 |
| 重复操作 | 推进、触发、确认、保存和读取处理中显示反馈并避免重复提交，失败后允许按实际状态重试 |
| 长列表 | 单位按兵种分组，使用稳定编号和局部滚动；无数量上限不代表全部图标和列表一次展开，也不代表任意规模性能承诺 |
| 只读模式 | 已结束结果和复盘使用只读展示，不能通过禁用编辑表单遗漏写入入口 |
| 操作可达 | 当前主要操作可见，图标按钮有中文可访问名称，键盘聚焦有轮廓，面板关闭后焦点可返回入口 |

右侧抽屉、信息浮层和底部弹层的互斥关系由页面集中协调，沿用当前原型同组切换方式，避免多个区块互相盖住主要操作。涉及未提交输入时不得悄悄提交；关闭与保留策略在前端架构中统一落实。地图输入方案由 Unity 客户端设计确定；保留网页部分可复用原 Pointer Events 路径，OpenHarmony 兼容性仍需实机验证。
