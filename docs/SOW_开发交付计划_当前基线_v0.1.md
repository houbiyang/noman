## 1. 项目目标

本项目建设一套运行在本机、可扩展到鲲鹏和 OpenHarmony 的虚构无人智能作战地图沙盘。Unity 负责三维地图、单位表现和用户交互；FastAPI、PostgreSQL、确定性规则模块和后续智能体服务负责权威状态、命令、快照、事件、建议和复盘事实。

交付目标分成三层：

1. **当前演示层**：地图、单位、三席位、准备、固定建议、时间控制、事件登记、持久化和复盘基础可以运行并通过测试。
2. **首版仿真层**：任务、地形、视野、路线、保障、抽象交战、事件效果、资源和评分具有可重复的确定性规则，并能由 Unity 页面观察。
3. **智能化扩展层**：总指挥和部队智能体能够在权限范围内读取状态、调用资料和提交候选建议；人工确认后，确定性规则执行实际动作并保留证据。

正式交付以第二层为首版产品门槛，第三层按模型、资料和预算就绪情况单独进入验收。

### 2.2 当前已知限制

- 任务节点目前是模板和展示状态，不能根据位置、设施或护送过程自动完成。
- 地图寻路目前是 Unity 本地视觉路径，后端没有权威通行、移动耗时、能耗或动态避让规则。
- 事件目前只登记，不改变设备、通信、天气、任务或资源状态。
- 固定建议来源为 `fixed_demo`，没有真实模型、资料检索、引用和智能体执行。
- 交战、战损、耐久、视野、发现、资源消耗和胜负评分没有正式实现。
- Unity 后端连接后的存档页目前显示数据库快照标识，完整的后端存档列表、恢复和退出操作仍需接入。
- 设置、战斗入口仍是页面预留入口。
- 鲲鹏、OpenHarmony、目标设备和规模性能尚未实测。

基线证据见 [现有功能后端验证记录](../backend/Verification/现有功能后端验证_2026-11-03.md)、[Unity 军队配置验证](../unity-client/Verification/军队配置验证_2026-11-03.md)、[Unity 客户端说明](../unity-client/README.md) 和 [后端说明](../backend/README.md)。

### 3.2 智能化范围（P1）

- 四类逻辑智能体：本方总指挥、侦察、陆兵、保障。
- 结构化报告、候选建议、工具调用、取消、超时和检查点恢复。
- 资料导入、解析、审核、版本、混合检索、重排序和原文引用。
- AI 建议绑定状态版本、角色、模型运行、资料证据和未知项。
- 模型服务不可用时，页面显示失败或等待，不使用固定文案冒充真实结果。

### 3.3 后续候选范围（P2）

- Army_Editor 编制和地图资产编辑、导入预览和导出。
- 单位级 Agent、开放推演和反事实分析。
- 多地图、战役目录、自然语言想定和高级配置。
- 鲲鹏服务端和 OpenHarmony 终端实机适配。

P2 不进入当前首版排期，除非在变更评审中重新确认范围、投入和验收标准。

## 4. 不包含范围

本 SOW 不包含实体无人设备、实体武器控制、真实战场部署、真实战斗效能预测、真实地理测绘、军用系统认证、公网运营、账号组织系统、商城支付、模型训练、强化学习和未经确认的第三方平台接入。

不因当前数据库已经有资料和向量表，就自动包含真实资料导入、真实模型推理或完整 RAG；这些内容必须按 P1 的准入条件单独验收。

## 5. 工作分解结构（WBS）

### WP-00 项目基线与决策锁定

**目标：**将当前需求、规则、接口、数据库、页面和验证记录锁定为可实施版本。

**工作内容：**

- 确认首版 P0 范围、责任人、投入、环境和接受人。
- 锁定 D-01 至 D-13 中影响当前批次的规则和技术决策。
- 统一地图坐标、仿真步、事件顺序、资源预算、评分和保存格式。
- 建立需求、代码、接口、测试和证据追踪表。

**交付物：**

- SOW 基线版本。
- 决策台账更新。
- P0 需求和接口冻结清单。
- 版本、环境和责任人清单。

### WP-01 地图与空间权威层

**目标：**让地图上的道路、地形、建筑、桥梁、部署区和任务点能够被确定性规则使用。

**工作内容：**

- 将当前地图摘要、道路和区域数据登记为场景版本。
- 明确高度、坡度、地表、道路、桥梁、水域、建筑占地和林地属性。
- 建立后端坐标转换、空间边界和通行查询。
- 输出可执行路线和失败原因，保存规则版本与地图版本。

**交付物：**

- 地图空间规则包。
- 通行与路线 API。
- 地图版本和摘要核对脚本。
- 路线正例、负例和边界用例。

### WP-02 军队、兵营与单位状态

**目标：**将当前本地军队配置转为可恢复、可校验的权威单位状态。

**工作内容：**

- 实现兵营放置、占地、部署区、道路接入和不重叠检查。
- 实现三类单位配置、数量、编队、任务和稳定 ID。
- 实现单位状态、能源、补给、耐久、可用性和持有关系。
- Unity 页面接收后端拒绝原因并刷新成功快照。

**交付物：**

- 军队和兵营规则模块。
- 单位状态 API 与快照字段。
- Unity 军队页面正式接入。
- 配置、部署、恢复和越权测试。

### WP-03 占点、时间与确定性行动

**目标：**让三点争夺和单位行动在固定仿真步中真实推进。

**工作内容：**

- 按 CQ-06 固定单步执行顺序，统一处理双方动作、占点资格、进度、计分和胜负。
- 实现陆兵完整占领步、敌点先中立化再占领、争夺停分、中断重置和人数不加速；发布前验收三点导航层、道路接入和可达性。
- 实现单位按路线移动、到达、等待、失败和恢复。
- 保存每一步的输入、规则版本、输出和事件。

**交付物：**

- conquest-v1 占点状态机与可配置测试规则。
- 单步执行器和状态机。
- 控制点动态态、占领进度和阻塞原因 API。
- CQ-TEST 占点独立预期轨迹与正负例。

### WP-04 地形、发现、事件与抽象交战

**目标：**完成“兵种和地图有关”的核心仿真能力。

**工作内容：**

- 定义三类单位在道路、水域、林地、建筑、桥梁和坡地上的通行属性。
- 实现视野、遮挡、发现三态、最后发现和通信未知。
- 实现设备故障、通信中断、天气变化和任务变化的起止及恢复效果。
- 实现陆兵抽象交战、目标资格、范围、动作占用、耐久和失效。
- 统一处理同一步内事件与行动的先后顺序。

**交付物：**

- 地形影响参数和规则包。
- 视野与通信规则模块。
- 事件执行器。
- 抽象交战和战损模块。
- 地形、发现、事件和交战验证用例。

### WP-05 资源、评分、结果与保存恢复

**目标：**使一局推演可以产生可解释、可恢复和冻结的结果。

**工作内容：**

- 实现能源、补给、库存与保障行动约束，记录真实消耗；占点局不沿用旧指令计费预算。
- 实现每点稳定控制的胜利分、全控连续计数和逐步计分事实；资源与战损仅作统计。
- 实现连续全控、双方同时达到阈值、第 60 步先结算后结束及同分平局，按 CQ-05 优先级裁决。
- Unity 页面接入后端存档列表、恢复、保存退出和结果页面。
- 验证恢复后的点态、积分、最近计分步、全控连续步、事件与待确认动作一致，不重复计分、不按离线时长补分。

**交付物：**

- 计分和结果模块。
- 后端存档、恢复、历史和复盘 API。
- Unity 保存、历史、结果和复盘入口。
- 完整运行态恢复测试。

| S7 集成与交付 | 第 17–18 周 | WP-07、WP-08、WP-09 | Unity、后端、数据库、测试和交接包 | P0 验收矩阵通过，遗留项有负责人和期限 |

若只有一名开发者，上述阶段应按依赖顺序执行并重新估算；若有前后端、Unity、规则和 AI 分工，可在 S2 后并行推进部分 S4、S6 工作，但不能跳过 S0 的规则和契约锁定。

## 7. 每阶段验收标准

### S0 验收

- P0 功能清单、非目标范围和优先级已签字或记录确认。
- D-01 至 D-05、D-07 至 D-10 中影响当前批次的内容已锁定。
- 人员、投入、环境、模型预算、资料样例和验收人已登记。
- 每项交付物有路径、负责人和验收方式。

### S1 验收

- 红、蓝、主持人能够绑定各自会话。
- Unity 地图显示的单位、任务、事件和时间线来自同一后端快照。
- 刷新、断连、状态冲突、权限错误和请求重试有可读反馈。
- 后端自动存档、手动存档和恢复入口完成一次真实页面验收。

### S2–S5 验收

- 规则模块使用固定版本输入，重复执行结果一致。
- 每个拒绝场景有稳定错误代码和不变状态证明。
- 每个成功动作有命令、快照、事件和可读回执。
- 读档恢复后不执行旧分支命令，历史记录不漂移。
- 结果页面只展示已裁决事实，未实现项不能显示伪造数值。

### S6 验收

- 模型调用可追踪运行 ID、输入摘要、模型版本、耗时、费用和失败原因。
- 资料引用有文档版本、片段位置、权限和原文摘要。
- 旧状态、越权资料、过期建议和未审核文档不能进入建议。
- 模型不可用、检索为空和输出不合规时均有明确失败状态。

### S7 验收

- Windows 本机和目标网页构建均完成运行验证。
- 数据库备份恢复和新进程恢复通过。
- 测试矩阵、缺陷列表、运行手册、配置清单和交接记录齐全。
- P0 遗留项全部关闭，P1/P2 项有明确的后续负责人和版本计划。

| 风险 | 影响 | 预防或应对 | 触发后的处理 |

| 视觉验收被旧缓存干扰 | 错误判断页面是否更新 | 每次构建核对时间、哈希、浏览器刷新和日志 | 重新构建并保存独立截图和日志 |

## 10. 变更控制

以下变化必须重新评估范围、时间和验收：

- 增加兵种、地图、任务模板或战斗模型。
- 修改坐标、仿真步、事件顺序、评分或资源预算。
- 改变主持人、红方、蓝方的可见范围。
- 将固定演示、替身模型或本地寻路升级为正式能力。
- 增加真实模型、资料目录、付费服务、目标设备或发布渠道。
- 修改数据库快照、分支、命令或接口格式。

变更记录至少包含：变更内容、原因、影响模块、影响文件、影响用例、增加或减少的交付物、排期影响、责任人和接受人。没有完成评估前，变更只进入实验分支或标记为待确认。
