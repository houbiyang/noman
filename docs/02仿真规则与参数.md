## 一、仿真规则

### 2. 三兵种职责与协作

#### 2.1 职责与能力边界

| 兵种 | 主要职责 | 已确认约束 |
| --- | --- | --- |
| 侦察无人机 | 沿已确认空中航线观察，在每个仿真步上报视野内按发现规则获得的信息 | 报告包含来源、对象、位置、状态与仿真时间；能源有限；不能替代运输和需要地面到场的任务；首版不赋予攻击动作 |
| 陆兵 | 沿道路行进，执行巡查、检查、保护等现场节点，并承担规则允许的对抗动作 | 具备耐久、对抗强度、作用范围、行动间隔、移动能力和补给余量等属性；首版执行第 10 节确定性抽象规则，数值及计算公式另定；耐久为零后失去任务能力 |
| 保障单位 | 为无人机恢复行动能源、为陆兵恢复补给余量，运输任务物资或撤离受损设备 | 库存有限；需要到达允许服务的位置；一次服务一个对象，服务占用 1 步；一次携带一个抽象任务对象；补给不自动修复耐久 |

#### 2.2 编队、任务与动作占用

1. AI 按任务节点需要组建编队，不固定要求各兵种数量一比一。一个兵种智能体可管理多个同类单位。
2. 每个单位同一时刻只属于一个正在执行任务的编队、承担一个主任务。改派须交接或结束原工作，并按既有人工确认规则处理。
3. 任务节点明确需要的能力、位置条件与单位状态。加入编队本身不直接满足节点条件。
4. 同一仿真步内，单位只执行一种主要动作：行进、现场操作、对抗或补给服务等互斥动作。动作切换暂停原动作，已完成节点保留。
5. 首版同一任务节点同一时刻由一个主要执行者推进；额外同类单位可负责其他节点、待命或接替，同类单位数量不直接成倍加速同一节点。
6. 对任务模板明确允许现场确认的普通任务点，陆兵可用 1 步进行本地确认；有效且适用于该节点的侦察报告可以满足对应的信息前置条件。本地确认不额外增加计分节点，也不揭示规则不允许显示的信息。
7. 协作依赖实际条件：现场操作需要到场，运输需要成功接收对象，信息共享需要有效报告成功送达，补给需要库存与合法服务状态。

#### 2.3 四类任务中的分工

| 任务 | 侦察无人机 | 陆兵 | 保障单位 |
| --- | --- | --- | --- |
| 区域巡查 | 提供区域观察与报告 | 到达并完成三个巡查区域节点 | 处理场景中出现的保障需求，没有需求时可待命 |
| 物资护送 | 更新检查点与任务对象的可见状态 | 执行模板要求的现场检查 | 持有并运输任务物资，通过三个检查点 |
| 设施保护 | 提供设施与区域状态报告 | 到场执行检查和保护节点 | 执行场景明确允许的恢复类操作，恢复能力与时长另定 |
| 受损设备撤离 | 按发现规则提供设备定位信息 | 完成接近和现场确认等操作 | 接收设备并送达撤离点 |

原有每项任务三个计分节点及成功、失败判定不变；观察、交接和保障等辅助动作不额外增加任务得分。辅助动作与计分节点的具体条件由任务模板明确。

#### 2.4 补给与对象持有

1. 保障单位服务后扣减库存；库存不足时需返回具备补充功能的本方兵营。
2. 服务双方须到达允许交接的位置并在服务完成前保持可服务状态。无人机须进入停靠状态，航行中不能直接增加能源。
3. 同一单位不能在同一仿真步同时完成补给和出发。保障单位服务或运输期间不能被其他任务重复占用。
4. 物资或设备同一时刻只有一个持有者；成功交接后才改变持有者，存档恢复不能复制对象。
5. 行动资源耗尽时，暂停依赖该资源的动作，保留位置和已有记录；不直接等同于耐久为零或产生安全扣分。具体消耗、恢复量与资源指令计费见第 8 节待定项。

#### 2.5 失效、降级与恢复

| 情况 | 影响与恢复 |
| --- | --- |
| 侦察无人机设备故障 | 暂停 5 步，停止新增该机观察；其他有效视野来源继续生效 |
| 通信中断 | 受影响报告标为未知 5 步，显示最后有效时间；不能用旧报告冒充实时状态；恢复后更新当前信息 |
| 陆兵失去任务能力 | 对应现场节点停止推进；AI 评估接替，其他成员继续满足条件的动作 |
| 保障单位故障或库存不足 | 对应补给、运输动作暂停；其他单位依自身状态继续可执行动作 |
| 任务目标被替换 | 旧进度保留供复盘，新目标从零开始；沿用既定任务变化计分规则 |
| 改派或接替 | 建议说明影响节点、可用接替者与期限影响，由本方操作员按重大调整规则确认 |

设备故障暂停 5 步继续按原规则自动恢复，保障单位不自动缩短这一持续时间。实际独立失效事件的安全扣分继续按 PRD 处理，单纯注入故障、暂停或资源不足不自动重复扣分。

编队状态分为正常执行、能力受限、等待协作、任务受阻和完成。等待或受阻时说明具体成员、节点和原因，不能以笼统异常代替。

### 3. 地图探索与信息共享

| 区域状态 | 展示与数据规则 |
| --- | --- |
| 未侦察 | 暗色遮罩，不展示尚未发现的动态对象 |
| 已侦察、当前不可见 | 地形和已知静态记录保持可辨，叠加较淡迷雾；对方单位仅可保留带时间的最后发现记录，不更新为实时位置 |
| 当前可见 | 明亮清晰，展示本方当步能够获得的对象与状态 |

1. 红蓝各自保存探索记录，模型输入、地图、列表和提示均遵守本方信息边界；主持人全局视图不作为双方 AI 的信息来源。
2. 多个有效观察来源共同覆盖区域时合并本方视野并保留报告来源。失去全部有效来源后，该区域转为已侦察、当前不可见。
3. 无人机离开后，曾经发现的对方单位不得继续实时移动。最后发现标记须显示时间并与当前可见单位区分。
4. 无人机具有较广视野，陆兵具有较小本地视野，保障单位具有基础本地视野。具体大小使用可配置游戏单位，待地图比例确定后锁定，不预填实际距离。
5. 暗区表示尚未侦察，不自动等同空中禁行区；无人机可进入规则允许的暗区探索，AI 不得预读其中尚未发现的对方单位。
6. 发现需要同时满足观察单位可用、对象在视野范围内、视线未被规则标记的阻挡遮蔽，以及信息满足对应共享条件。地形是否阻挡视线由场景属性明确提供，不能仅由图片纹理推测。
7. 失去有效视野当步立即停止对方实时位置及状态更新，改为带时间的历史记录；重新发现后使用新观察结果，旧记录仍保留在复盘中。地图、列表、AI 输入与方案解释遵守同一信息边界。
8. 通信中断期间按既有规则将受影响共享报告标为未知 5 步，不能让总指挥继续接收该来源的伪实时数据；本地信息与可共享信息的具体接口在技术设计中区分。

### 4. 兵营部署

#### 4.1 数量、时机与权限

1. 首版每方放置一个兵营，在开局准备阶段可放置、移动或撤销；开始后位置固定，不新增兵营或部队。
2. 双方部署区由地图预设，面积、可建造地形和道路接入条件保持可比；玩家只操作本方兵营与部队配置。
3. 每方三个初始单位及准备阶段新增单位均归属本方兵营。配置新增部队不扣建造资源，不设单位数量上限。

#### 4.2 放置合法性

1. 检查完整建筑占地，全部位于本方部署区内且可建造；不能只检查中心点。
2. 占地不能与河流、高山、道路、桥梁或其他占用对象重叠；具体形状、尺寸和占用范围由地图设计提供。
3. 兵营具有建筑占地、地面出入口和无人机停靠点。地面出入口可接入道路网，停靠点处于可飞区域并能作为合法航线端点。
4. 放置时自动匹配允许的连接点，移动后重新检查。接入距离阈值待地图比例确定，不预填实际米数。
5. 预览须显示可以放置或具体失败原因，如占地越界、位置占用、缺少地面出入口、停靠点不可用。

#### 4.3 开局与出发

1. 双方兵营、部队配置、任务与场景配置通过检查后，主持人可进入开局。首次任务分配尚未确认时保持暂停，确认后才推进执行。
2. 按已确认方案，地面单位从地面出入口进入道路网，无人机从停靠点沿空中航线出发。
3. 未出发单位处于兵营待命，在兵营列表和数量标记中展示；不要求把所有待命单位图标堆到地图上。
4. 出场动画不额外消耗仿真步，真实出发时刻、成员及方案均需记录。
5. 兵营提供停靠与库存补充功能；补给扣费和容量待资源规则统一确定。
6. 本方始终可查看本方兵营。对方按发现规则显示建筑，发现建筑不公开待命部队、配置及库存；主持人可看双方全局。
7. 首版兵营只承担部署、出发、停靠和补给功能，不参与伤害结算，不设置摧毁兵营获胜条件；继续使用任务、资源和安全三项判胜。后续如增加兵营损坏或恢复，需另行确认。

### 5. 道路与空中航线合法性

#### 5.1 导航数据

地面道路由路段和路口组成，道路是地图实体；选中部队时高亮其已确认行进路线。空中路线由当前位置或兵营停靠点、若干途经点和有效任务目的地组成。两类路线分别使用对应的可通行数据。

地图插画不直接充当通行判定。空中可通行区域和禁行区域由场景数据明确标记；首版按二维区域判断，高山是否阻挡空中路线由可飞标记决定。

#### 5.2 空中航线检查

| 检查项 | 通过条件 |
| --- | --- |
| 起点与终点 | 起点是无人机当前位置或兵营停靠点，目的地对应有效任务位置或已安排的停靠、补给点 |
| 地图边界 | 所有途经点及连接线段处于可游玩范围内 |
| 可飞区域 | 整条航线不穿过地图明确标记的空中禁行区域 |
| 单位状态 | 无人机可行动，未被互斥动作占用 |
| 能源条件 | 能源满足当前计划航段及已安排停靠、补给条件；具体消耗模型待定 |
| 任务条件 | 目的地、任务及期限仍有效 |

系统先检查路线是否合法，AI 再按第 9 节选择；AI 的文字解释不能替代规则检查。对已知条件与待核验条件分别说明，不依靠隐藏对象或主持人全局数据排序。

#### 5.3 重新检查与展示

1. 任务目标、单位状态、能源条件或路线通行状态变化时，重新检查受影响路线；不要求每步无条件重新选择整条航线。
2. 天气变化继续适用已确认的进度延迟 5 步，不自动增加封闭空域效果。
3. 常态显示道路及已确认路线，点选单位查看其当前航线；查看 AI 方案时展示候选路线、预计耗时与选择依据。
4. 路线失效时记录原因及相关事件。需要改派等重大调整时进入既定人工确认流程。

### 6. 存档、复盘与字段范围

存档与复盘需按同一仿真步保存和恢复：兵营位置及连接点、待命与已出发单位、编队归属、当前动作、任务节点、能源与补给库存、对象持有关系、路线及航段进度、双方独立探索状态、报告及最后有效时间、持续事件、待确认建议和评分记录。读档后暂停且继续按角色隔离数据。

| 对象 | 必须表达的信息 |
| --- | --- |
| 兵种模板 | 类型、职责、能力标签、移动方式、可配置属性；数值未定项不可伪填 |
| 部队实例 | 编号、阵营、兵种、所属兵营、编队、位置、当前动作、任务、可用状态、能源或补给、有效时间 |
| 编队 | 成员、任务、节点分工、能力依赖、状态、受阻原因 |
| 兵营 | 阵营、占地、地面出入口、无人机停靠点、待命列表、补给功能状态 |
| 观察报告 | 来源、对象、获取时间、最后有效位置与状态、可见范围、可靠性状态 |
| 运输对象 | 对象编号、当前持有者、交接记录、交付状态 |
| 路线 | 编号、移动类型、途经点或路段、目的地、合法性、单位进度、相关事件 |

字段名称、存储格式与接口在技术设计中确定。本表规定可追溯的信息，不直接规定数据库结构。

### 7. 行为验收案例

| 编号 | 场景 | 应观察到的结果 |
| --- | --- | --- |
| RULE-01 | 兵营中心在区内，但占地越界 | 拒绝放置并解释占地越界 |
| RULE-02 | 兵营占地合法，但缺少道路接入或可用停靠点 | 阻止准备完成并显示具体原因 |
| RULE-03 | 开局配置三个初始单位及额外单位 | 待命列表数量正确；确认方案后分别从对应出发点出发，不直接在任意地图点生成 |
| RULE-04 | 多个来源观察同一区域，随后一架无人机离开 | 只要仍有有效来源，区域保持当前可见；全部离开后变为已侦察、当前不可见 |
| RULE-05 | 对方单位失去本方视野后移动 | 本方不能继续收到实时坐标；最后发现记录保留时间，AI 输入遵守同样边界 |
| RULE-06 | 无人机故障或报告通信中断 | 分别体现暂停 5 步或报告未知 5 步，其他有效来源不被一起删除 |
| RULE-07 | 两支保障单位同时申请服务同一对象 | 不重复执行、不重复恢复资源；库存与服务记录一致 |
| RULE-08 | 运输对象成功交接后存档、读档 | 同一对象只有一个持有者，库存与任务进度不重复增加 |
| RULE-09 | 空中路线端点合法，但中间线段穿过禁行区域 | 整条路线判为无效并标明受阻段 |
| RULE-10 | 航线经过允许飞行的暗区，或注入普通天气变化 | 暗区不自动阻断；AI 不获取隐藏对象；天气只施加已定义的 5 步延迟 |
| RULE-11 | 保障单位故障且 AI 提议改派 | 相关运输暂停，其他可执行动作继续；重大调整等待操作员确认；既有完成节点保留 |
| RULE-12 | 推进后存档并恢复 | 同步恢复兵营、编队、路线、资源、探索三态与报告，整局保持暂停 |
| RULE-13 | 对比可执行、信息待核验与不可执行路线 | 分别标记原因，不把未知当作通行保证，不把已确认无效路线纳入可执行方案 |
| RULE-14 | 改变主持人可见但本方未知的对象状态 | 本方选路与解释不因隐藏数据直接改变；来源和权限可追溯 |
| RULE-15 | 路线到达快但补给或协作等待较长 | 比较完整预计任务时间，按已确认偏好排序，不只看行程 |
| RULE-16 | 对象在名义视野范围内，但被场景视线阻挡 | 未满足发现条件，不产生当前可见报告；阻挡由明确数据判定 |
| RULE-17 | 对方在当步离开本方全部有效视野 | 当步停止实时位置与状态更新，重新发现后采用新结果 |
| RULE-18 | 申请对兵营或未纳入资格表的对象执行对抗 | 拒绝结算并说明对象资格原因，不新增兵营获胜条件 |
| RULE-19 | 交换同一步红蓝动作处理顺序 | 确定性抽象结算得到相同结果，不产生先处理方额外行动 |
| RULE-20 | 单位耐久降至零，随后再次读取或推进 | 停止动作并记录一次独立失效；不重复扣同一次安全分，也不直接替代任务胜负 |
| RULE-21 | 单位路径经过任务、视野或接触检查区域但终点位于其外 | 路径过程被检查，不因仅比较起终点漏掉中途事件；不额外增加仿真分钟 |

尚需具体数值的案例，须先使用明确的测试场景参数，并标注测试参数，不得将其视为已锁定产品默认值。

### 9. AI 路线选择依据（已确认）

本节按用户对四项规则的确认执行，规定行为与排序原则；具体算法和数值按第 8 节继续设计。

1. **候选来源**：规则模块根据道路网或空中可飞数据生成候选，AI 比较与解释。界面并列显示代表性候选，具体数量由 UI 设计确定，不据此限制部队数量或声称枚举全部路线。
2. **先检查条件**：候选必须经过对应移动规则检查，满足单位能力、已安排补给和资源条件；区分当前可确认的条件和待核验的信息。只使用本方已知或场景公开的信息，不依靠隐藏对象及主持人全局状态排序，也不声称掌握暗区的动态情况。
3. **预计时间**：计算移动、已安排的停靠补给、协作等待和现场操作等已知耗时，说明是否有望在任务期限内完成；不能只比较到达时间。未知耗时明确列出，不虚构概率。
4. **选择顺序**：优先比较满足期限及资源条件的候选。默认按时优先，先比较预计完成时间，再比较资源消耗；可提供节约优先，先比较资源消耗，再比较完成时间。两种偏好都不能绕过合法性与期限检查。结果相同则优先保留当前路线，再以稳定编号排序，避免无理由来回切换。
5. **重新选择**：目标、单位状态、能源或通行条件变化影响当前方案时才触发重评估。其他候选略有改善而当前方案仍满足条件时，保留当前路线；单纯展示动画或镜头移动不触发重选。新路线从单位当前真实位置开始，不跳跃到另一路段。
6. **人工确认**：首次方案和涉及目标变化、单位改派或新增资源指令超过既定阈值时仍须确认；允许范围内的路线调整记录依据。现有人工确认规则不能被候选排序或模型建议绕过。
7. **没有合适方案**：分别提示没有有效连接、单位或资源条件不满足、预计无法按时完成、信息仍待核验等原因；AI 提供原因与可供处理的选择，不能自动放宽规则，也不能仅凭预测超时直接宣判任务失败。任务失败继续按 PRD 的截止与不可恢复条件判断。
8. **比较与留痕**：方案展示路线、预计完成时间、资源变化、待核验信息、选择理由及替代方案。采用后记录对应仿真步、观察来源、方案与人工处理，供存档和复盘使用。

候选结果分为可执行、信息待核验、不可执行。当前已知条件通过的方案可进入比较；存在未确认动态条件时必须标明，不能保证可行；已确认越界、断路、禁行或单位条件不满足的方案予以排除。路线预测不替代既有任务失败判定。

### 10. 首版抽象交战判定（已确认）

#### 10.1 范围与动作资格

首版实现不同阵营陆兵之间的地面对抗。侦察无人机和保障单位继续承担观察、补给及运输；其是否可以成为对抗对象须另设对象资格表确认，未配置资格不得参与结算。兵营不参与伤害结算。

| 检查项 | 执行动作的必要条件 |
| --- | --- |
| 阵营 | 参与双方属于不同阵营 |
| 对象资格 | 对象类型属于本版明确允许范围，首版为陆兵对陆兵 |
| 信息 | 执行单位已按规则获得目标的当前有效信息，历史位置不等同当前可见 |
| 距离 | 满足场景明确配置的游戏作用范围 |
| 状态 | 执行单位可行动，耐久及所需资源满足条件 |
| 动作占用 | 当步未执行互斥的行进、补给或现场操作 |
| 方案权限 | 动作位于已确认方案允许范围内，不能绕过人工确认 |

#### 10.2 结果与失效

1. 同一仿真步统一结算，不因程序先处理红方或蓝方而额外给予行动。单位每步只执行一个主要动作，对抗占用该动作。
2. 首版使用确定性抽象结算，不加入随机命中或暴击；具体耐久、对抗强度、作用范围、行动间隔、消耗及计算公式待参数和技术设计明确。
3. 记录参与单位、前后状态、资源变化、原因和仿真步；动画展示已产生的结果，不自行决定结果。
4. 耐久为零后停止移动、现场操作与对抗，形成一次独立失效记录，按既有安全分规则计分。反复读取或推进不能重复计算同一次损失。
5. 临时设备故障、补给不足与耐久为零分别处理，不合并为同一种损失。交战本身不额外增加任务得分，不替代任务、资源、安全综合胜负规则。

### 11. 统一时间与路径过程（已确认）

每步仍推进 1 仿真分钟，移动、发现、动作、结果、任务、计分和存档对应同一仿真步。动作互斥、同一步统一结算和信息权限共同适用。

实现时必须检查单位经过的路径过程，不能仅比较起点和终点而漏掉途中任务、视野或接触检查区域。内部检查与视觉插值不额外增加仿真分钟；具体执行阶段和几何检测算法由技术设计明确，不因中途发现对象自动授予当步额外动作。

### 12. 首版技术执行边界

首版采用 [05 系统架构](05系统架构.md) 确定的 Python + FastAPI 应用服务、LangGraph 编排、混合 RAG 和 PostgreSQL + pgvector。Unity 负责三维总览、单位跟随和战斗表现。规则模块维护权威状态，单位状态机执行经确认动作；模型及检索不直接修改坐标、资源、视野或得分。

游戏快照、事件、已采用方案与工作流检查点分别管理，采用前校验对局分支和状态版本；旧状态模型结果、重复提交与工作流恢复不能重复执行动作。具体接口、事务、存储与模型版本按配套技术设计继续细化，现有行为及待定游戏参数不因架构选型改变。

## 二、执行细则与参数草案

### 1. 状态与范围

2026-10-26，设计草案。已确认规则仍以 PRD 和仿真规则规格为准；本文件提出可审阅的执行方案，不把阶段排序、事件区间或计费建议自动批准。待决编号见 `00文档索引与决策台账.md`。

只描述虚构数字游戏。不得用真实距离、真实打击参数或资料中的规则替代本项目配置。未知配置阻止依赖动作，不通过猜测继续。

### 2. 时间、提交和运行控制

- `simulation_step = k` 表示已提交的第 k 仿真分钟，初始为零，最多六十。
- 一次合法单步从已提交状态 k 计算下一状态 k+1；对用户只提交完整成功或明确失败，失败不增加一步。
- 同一 k 可有准备、暂停、建议处理、保存等多个修订；是否过期不能只比较分钟。
- “继续”由唯一有效服务执行者依后续确认的现实节奏发起单步，轮询和地图动画不发起结算。
- 暂停命令不能回滚已提交步骤。并发暂停与推进须在命令边界串行裁定，返回实际结果；不声称页面按下瞬间撤销正在提交的步骤。
- 外部模型等待不占游戏事务。先取得本方允许输入，异步分析；采用前再核对状态、权限和方案合法性。
- 游戏步骤确定性与模型生成可变性分开：给定同一配置、领域状态和已采用动作，规则结果应一致；不要求模型每次生成同样文字。

上述提交机制需与后端及 API 草案一起确认，不据本文安装执行器或迁移数据库。

### 3. 单步执行阶段建议（D-01）

以下是建议顺序，供确认及写独立预期使用。阶段内容明确后，才能实现依赖先后关系的正式结算。

| 阶段 | 读取和工作 | 约束／待确认边界 |
| --- | --- | --- |
| S0 准入 | 主持人控制、阶段、预算、幂等、分支、版本、待确认阻塞 | 失败不消耗仿真时间或资源 |
| S1 时间事件 | 将适用于本次转换的脚本触发、到期恢复和环境影响转为明确作用集 | 生效区间和同类叠加由 D-02 决定；同实例不重复触发 |
| S2 行动意图 | 从共同依据检查已采用计划、可用状态、主任务和互斥主动作，冻结当步行动集合 | 不按红蓝先处理产生额外行动；模型不直接创建结果 |
| S3 路径过程 | 计算合法路段／航段、能源与经过区，采集任务接触、观察机会和受阻事实 | 不能只比端点；中途观察不授予第二个主动作 |
| S4 动作结果 | 对允许现场操作、服务交接及陆兵间抽象对抗统一计算前后值 | D-01 要明确新观察能否作用于本步既有意图；建议只授权后续动作，避免同一步插队 |
| S5 观察与协作 | 合并有效来源、应用阻挡和通信规则，更新当前／历史／未知及能力依赖 | 失去全部来源当步停止实时更新；终点观察不能抹掉途中已发生记录 |
| S6 任务与终结 | 从实际位置、动作完成和设施状态检查节点、目标修订、截止及不可恢复 | 第六十步完成与截止先后、保护的持续要求由 D-05 决定 |
| S7 计分与记录 | 从唯一执行、节点与损失事实计算分项，形成事件和完整快照 | 不因读取或动画重复扣分，历史使用当时版本 |
| S8 原子提交 | 命令结果、快照、事实及成功自动保存入口一致提交 | 写入失败不留半份世界；提交结果不确定先核对原命令 |
| S9 通知与分析 | 提供角色投影，登记必要的重新分析任务 | 私有状态不泄露；模型结果晚到仍需采用前检查 |

D-01 确认记录须覆盖：每阶段使用步初还是阶段结果、同类动作冲突、服务对象失效、途中发现与接触、节点完成和同一步损失。不能只批准一张流程图而没有边界样例。

### 4. 五步事件和重叠建议（D-02）

#### 4.1 建议的区间表达

建议事件记录 `triggered_at_step`、`first_affected_transition`、`last_affected_transition` 和 `recovered_at_step`，区分“第 k 步点击触发”与“从 k 到 k+1 的转换”。

供审阅的选项 A：在已提交 k 步触发的五步故障，影响目标转换 k→k+1 至 k+4→k+5，五次转换结束后恢复，下一次转换可行动。选项 B：触发当步即算一次影响，影响集合及恢复点相应提前。推荐 A，因为用户在已提交状态进行手动注入时，不必追改过去的一步；最终按确认结论执行。

例如 k=12 的 A 方案影响五次转换，恢复记录位于提交第 17 步之后。k=58 时仍最多运行到 60；剩余事件保存为结束时状态，不补跑第 61 至 63 步。这个算例只解释方案 A，不是已确认默认行为。

#### 4.2 事件组合表待确认

| 组合 | 建议处理 | 不可默认的行为 |
| --- | --- | --- |
| 同一事件实例重试 | 返回原结果，不增加影响 | 按请求次数重复注入 |
| 同单位不同故障实例 | 保留来源，按明确区间并集暂停，显示最晚结束 | 直接累加十步或忽略第二事件 |
| 故障和通信中断 | 分别保存作用，动作与报告按各自条件处理 | 全部混成失效并扣分 |
| 同任务多次天气 | 必须明确延迟是区间阻塞还是截止／工作量调整 | 既停五步又加五步，双重延迟 |
| 多次任务变化 | 顺序由提交修订决定，旧目标留痕，新目标从零 | 合并旧进度或按模型偏好忽略 |
| 解除一个来源但其他仍有效 | 仅恢复已无剩余作用的能力 | 删除全部事件影响 |

天气“延迟五步”的实现方式、受影响节点及是否阻塞移动尚须确认；不得额外增加禁飞或伤害。所有持续时间按仿真转换，不按真实停机时长计算。

### 5. 资源计费建议（D-03）

已确认：每方预算二十条；每条已执行资源使用指令扣五分；准备配置免费；提出、预览、驳回不等于执行。未确认：什么动作是一条、按单位还是分组、持续动作与改线如何计。

| 需裁定项 | 建议口径 | 必需样例 |
| --- | --- | --- |
| 计费粒度 | 可考虑“一个单位接受一条被定义为计费的主动作指令”；最终由计费表决定 | 一个单位与十个单位执行同任务分别计数 |
| 持续行进 | 同一已计费指令跨步持续不重复计；若改派生成新指令，依计费类型判断 | 连续五步、暂停继续及读档不重复 |
| 补给和交接 | 明确发起服务、运输、交接是否分别计费；不把库存减少自动当一条 | 服务成功、失败、重复请求 |
| 部分失败 | 未执行不扣；已经实际执行而任务失败，是否扣须按指令事实判断 | 执行失败前后和事务回滚区分 |
| 方案新增量 | 建议按稳定指令身份比较新增集合，不单用新旧总数相减 | 旧五条全部换成另五条，不能被净增零掩盖 |
| 预算不足 | 拒绝超预算执行，不按实际单位数静默裁掉后半部队 | 批量采用和并发采用 |

推荐先填写动作计费表：动作代码、适用兵种、成功事实、计费次数、持续动作规则、替代指令关系。只凭“移动、补给都算资源”无法实现统一预算。D-03 未确认前，评分测试可直接注入已知合法执行事实，但不能证明完整指令收费已验收。

| 陆兵抽象对抗 | 耐久、强度、范围、间隔、消耗、结算公式 | 抽象游戏量 | 不推测真实数据，不参与未配置结算 |
| 设施和节点 | 各模板位置条件、现场耗时、保护正常判定和允许恢复 | 稳定对象、状态及步数 | 不能仅靠到达或动画完成 |
| 运行样例 | 单位、报告、路线、事件、原文和快照规模 | 数量、字节与实测耗时 | 基础范围以外不承诺性能 |

每个参数另需：`parameter_key`、类型、适用对象、空值含义、合法区间、当前值或“待定”、规则版本、确认来源。源码硬编码不能成为参数确认来源。

### 7. 任务边界与恢复（D-05）

- 巡查：三个区域到达是否还需现场一步操作，必须由节点定义写明；报告不自动替代地面要求。
- 护送：运输对象实际持有、检查点顺序和地面检查条件分别定义，不能把无人机经过当物资经过。
- 保护：第 20／40／60 步正常的检查已确认；“仅检查该时点”与“持续整段正常”不能混用，待规则负责人选择。
- 撤离：定位、接近、到达撤离点为三计分节点；接收交接是依赖条件，不新增第四计分节点。
- 最后节点完成意味着成功 100；失败的三个节点最多 60。未完成最终目标的条件需用模板区分，不能同一次最终完成同时标失败。
- 第六十步内能否先完成再检查截止须明确；建议先检查该步合法完成结果，再对未终结任务判截止，待确认后同步用例。
- 不可恢复失败需给出无可用单位／路径、截止与已无恢复机会的具体证据；仅路线估时差或模型悲观不足以判失败。
- 驳回新目标建议后，目标是否已替换与方案是否采用是两件事；保留目标事件和驳回事实，后续等待及重建议由协议定义，不悄悄恢复旧目标。

### 8. 规则不变量与验收入口

始终检查：一个单位一个主任务和活动编队、每步一个主动作、唯一持有、库存守恒、同实例不重复作用、同损失不重复计分、角色信息边界、六十步上限及旧分支无写入资格。

固定样例与独立预期见 `11测试与验收.md`。涉及 D-01 至 D-05 的断言在确认前标阻塞；其他既有行为可先验证。不把新建议写成“已通过规则”。

### 2. 编制、模板与装备资产校验草案

#### 2.1 资产模板与运行实例

1. 组织节点、兵种模板、装备模板、编队和运行单位使用各自稳定标识；名称、层级、兵牌和列表序号仅作显示，不作为身份或权限依据。
2. 编制树编辑涉及父子关系；运行编队涉及当局任务协作。导入编制树不直接建立活动编队、不自动分配任务、不增加逻辑智能体。首版仍为每方四个逻辑智能体。
3. 一个父节点汇总子树时，须区分节点自有数量、子树合计和实际实例化数量。父子重复选择不能重复创建运行单位；具体展开粒度及统计方式待资产契约确认。
4. 复制子树产生新的节点身份；共享模板引用是否保留须明确记录。复制、重命名不能把两个运行单位合并，也不能复制其运输对象或资源账。
5. 编制导入只生成准备草稿。红蓝只能导入本方允许的配置，最终仍检查本方唯一兵营、初始三单位、部署合法性及开局后禁止新增等既有条件。

#### 2.2 导入和编辑检查

| 检查主题 | 规则草案 | 拒绝或反馈要求 |
| --- | --- | --- |
| 树结构 | 节点唯一；父节点存在；不能把祖先移动到后代；不能形成环或跨阵营挂接 | 保留当前合法树，定位非法节点和父子关系 |
| 数量与统计 | 使用有限、合法的非负整数；若支持区间，须明确区间只作显示还是有已确认的实例化规则 | 不从 min/max 自动随机产生兵力；不静默截断超出可处理规模的单位 |
| 类型与能力 | 模板类型、能力标签和可执行动作来自本项目有效版本 | 源项目的无人机兵牌不赋予攻击能力；未支持兵种不能回退成其他可执行兵种 |
| 装备引用 | 通过稳定 ID 与版本解析装备，检查依赖是否齐全 | 重名不能自动绑定；缺依赖、同 ID 冲突或删除引用均列出原因 |
| 数值与缺失 | 明确类型、量纲、边界和空值；零与未配置分开 | 不把零能源/补给回填为默认满值；不将人数、装备数、耐久混为同一字段 |
| 运行一致性 | 开局绑定资产版本，运行快照保持该版本含义 | 编辑资产库不能追改已开始对局或冻结历史；迁移规则须另行确认 |

首版三兵种的职责和对象资格不因装备属性增加而扩大。编制、装备中的人员数、车辆数及图片统计不会自动进入任务分、安全分或资源指令预算。

### 3. 地图、场景与 Unity 表现约束

#### 3.1 地图转换和版本绑定

地图编辑结果应先形成转换草稿，说明源格式及版本、对象 ID、坐标原点、轴向、尺度、有效边界和转换结果。二维栅格、道路折线或图片不能直接当作 Unity 场景与后端规则的共同完整地图。

| 数据层 | 业务约束 |
| --- | --- |
| 地形外观和 Unity 资源 | 用于显示；不得单凭模型、纹理、阴影或碰撞体推断可通行、已发现或受伤 |
| 道路与地面通行 | 显式提供节点、连接与限制；路段断开、越界等须能定位，规则检查完整经过路径 |
| 空中可飞/禁行 | 显式定义区域与边界；源项目栅格索引须按稳定地形 ID 转换，不因数组换序改变含义 |
| 视线与探索 | 规则阻挡层和角色观察快照分别管理；Unity 遮挡不自动造成服务端失视 |
| 部署与任务对象 | 区域、兵营连接点、设施、任务点、撤离点具有合法几何和有效引用；多边形等形状按选定格式校验 |
| 资产依赖 | 地图资源、场景定义和规则版本可追溯；无法解析的引用不能静默忽略后继续开局 |

地图转换必须报告原对象数、成功映射数、拒绝项和未支持项；转换失败不能替换当前有效场景。源项目可编辑多个出生区、据点或补给点，不表示本项目首版已支持多兵营、票数争夺或额外任务节点。

#### 3.2 相机与仿真时间

三维总览、单位跟随、切换镜头、画面帧率和动画时长均不参与业务计时与结算。业务平面到 Unity 世界坐标的轴向、尺度、显示高度和精度由场景映射配置定义；具体值待确认，不默认等于实际距离。

跟随目标必须当前可见；失视、对象失效、切角色或切分支后停止旧实时跟随并清理旧特效。历史记录可以保留最后有效位置，不能继续引用目标实时 Transform。选点转换回业务坐标后仍由后端检查部署、路线和对象资格。

### 4. 命令草稿、采用与执行回执草案

#### 4.1 同一校验入口

下表中的命令是规则执行意图，不新增操作员逐次驾驶、直接移动或开火玩法。首版人工输入仍限本方分工、优先级与资源额度；任何未来手动动作菜单都要先明确范围，不能由 Gentactix-DSH 的人工优先策略自动授予。

| 来源 | 进入执行前的要求 |
| --- | --- |
| 操作员确认或修改的建议 | 具备本方处理资格，涉及对象与修改字段合法，依据版本有效，预算及任务期限检查通过 |
| 总指挥与兵种智能体 | 只生成候选，核对已采用方案范围；首次和重大调整仍等待人工 |
| 规则策略或默认待命 | 使用已确认规则和可解释来源；不能用默认方案替代 AI 不可用时被阻塞的首次分配 |
| 后续单位级 Agent | 绑定授权单位与观察上下文；不能越过已采用方案、单主任务或本方人工处理 |

队列保存、自然语言解析、地图预览和模型试算均不等于采用或执行。建议把以下顺序落实为统一检查：请求结构 → 会话与角色 → 对局/分支/状态版本 → 对象与可见性 → 动作白名单及方案资格 → 主任务/占用/资源/路线/期限 → 幂等与并发 → 完整提交及回执。具体事务安排仍由 API 和后端契约确定。

#### 4.2 生命周期与冲突

| 业务状态 | 含义与处理草案 |
| --- | --- |
| 草稿 | 尚未采用；编辑输入使旧预览与旧解析依据失效 |
| 待人工处理 | 建议具备处理上下文；处理完成前依既有规则阻塞推进 |
| 已采用/待执行 | 已通过采用校验；只有在执行时资格仍有效才可进入当步动作 |
| 执行中 | 记录指令、单位与执行步；持续任务沿当步预算推进，不能瞬移或每步新增一条采用事实 |
| 受阻 | 位置、资源、事件或能力条件不满足，记录原因；恢复资格和重评估方式须按确认规则处理 |
| 已完成/失败/过期/取消 | 分别记录实际结果与原因；不能仅以动画结束或模型文本判断完成 |

状态名称是领域语义草案，不直接新增 API 枚举。每单位当步最多一个主要动作；多个来源竞争同一单位时先检查当前已采用方案和本方人工决定，不能按响应到达先后静默覆盖。替换方案、取消或重排仍须符合改派和重大调整规则；未执行草稿的撤销不代表已提交世界的回滚。

命令受阻或失败不直接判整项任务失败；任务继续使用截止和不可恢复条件。未满足对象资格的源项目动作不能因导入出现而执行。资源指令计费仍待 D-03，队列长度、调用次数和动画次数都不是自动计费口径。

#### 4.3 去重、版本与证据

建议命令关联稳定身份、来源、对象、操作类型、参数、对局/分支/依据版本、方案与人工处理记录；执行回执关联实际提交版本、仿真步、前后值、执行事实及原因，字段名称以 [06 接口契约](06接口契约.md) 为准。

同身份同输入的重试应可核对原结果；同身份不同输入不得当作新指令继续提交。网络超时或取消请求不证明事务未提交，需先查询执行结果。重复读取、队列刷新、暂停继续和存档恢复不能重复执行或重复计费。

### 5. AI、资料与数据完整性

1. 原首版继续保持每方四个逻辑角色。后续单位级会话只作为授权提案实现，不自动增加逻辑角色或为每个单位建立不受预算约束的模型循环。
2. 模型输入、工具观察、检索证据、缓存、运行摘要和轨迹按角色及上下文隔离。工具可读取允许状态或试算候选，不直接写单位、规则参数、预算、权限、会话版本或主战局。
3. 程序规则、当前观察、历史报告、人工输入、模型推断和资料引用分别标来源。解释中的“已发现、完成、执行成功”等断言必须能对应程序事实；不能从模型叙事补出缺失状态。
4. 候选结果检查单位身份、名单、字段类型、有限数值、资源边界、运输对象唯一持有和事件唯一性。单位遗漏或未知字段不能自动解释为损失、退役或零值；校验失败保留当前有效状态并报告原因。
5. 已批准的原方案按既定状态机继续与否，由当前阶段和规则决定。模型失败、超预算、证据不足或取消不能自动解除关键建议待处理状态。
6. 模型运行预算、超时、工具白名单、重试次数、取消截止点与结果保留方式需单独配置；没有完成记录和执行回执时，不能把发起调用、取得文本或收到取消请求写成执行完成。

运行进度、模型 token/耗时、队列状态与规则结算状态分开展示，调试指标不作为游戏得分或行动时间。

### 6. 存档、导入与分析分支

#### 6.1 保存和恢复

保留首版游戏快照、事件、采用方案与独立工作流检查点的区分。若使用数据库，状态、命令事实与快照按既有事务契约保持一致；若保存导出文件或文件检查点，再采用临时写入、校验和原子替换方案。不能用一个 JSON 文件替换已经选定的数据库事务，也不能认为工作流恢复等于整局恢复。

恢复应核对场景、规则、资产与格式版本、对象引用、当前步、资源/库存、活动动作、探索、待处理方案及事件作用；成功后进入新分支并保持暂停，旧分支响应、队列执行资格与模型候选均需重新核对。

#### 6.2 导入预览

| 阶段 | 规则草案 |
| --- | --- |
| 解析与校验 | 检查格式、有限数值、身份唯一性、依赖、场景/规则版本与只读/可恢复资格；不执行包内脚本或工具指令 |
| 预览 | 显示来源、版本、任务、步数、单位数量、缺失依赖与兼容问题；预览不切换当前对局 |
| 确认 | 由有权主持人显式确认，核对预览仍对应原内容和有效上下文；具体摘要/哈希协议待契约确定 |
| 应用 | 按选定格式新建对局或恢复分支，冲突不能覆盖既有身份；失败保留当前有效局与可读取存档 |

导出的数据范围按角色和用途限定。对局中不能以普通导出、历史列表或 Unity 场景对象取得对方隐藏状态；主持人备份属于受控数据，不能直接交给红蓝客户端当作角色响应。

#### 6.3 分析分支（后续 P2）

从冻结历史快照创建独立分析上下文，记录来源步、规则/场景版本、干预项、保持项与结果。几何对照只说明所选几何指标变化；规则对照需使用同版规则和合法输入；模型对照保留模型与提示版本、调用记录及可变性说明。

只读分析不改变主战局，不增加主局动作、资源、分数或胜负记录。未来若开放可写演习分支，应与只读复盘区分，以新的分支身份运行；启动资格、权限、计分展示和历史保留须另行设计，不能直接采用源项目开放模式来绕过本项目规则。

### 7. 融合参数登记与发布条件

下表扩展第二部分第 6 节的参数登记要求。键名用于说明配置职责，是待确认建议；不将其当作已存在的文件、字段或产品默认值。

| 参数组/建议键 | 必需内容 | 当前状态/关联决策 | 缺失或不兼容时 |
| --- | --- | --- | --- |
| 资产映射 `asset_mapping_version` | 源格式版本、目标 Schema、稳定 ID 映射、类型与能力映射、装备依赖 | 后续候选；PRD-24、25；D-07 | 拒绝未支持内容，保留原配置 |
| 编制展开 `organization_expansion_policy` | 层级与实例化粒度、父子统计、复制身份及数量区间语义 | 后续候选；PRD-24；D-07、D-12 | 不猜测实际单位数，不静默截断 |
| 地图转换 `map_mapping_version` | 坐标原点/轴向/尺度、边界、地形 ID 与道路/区域映射 | PRD-26、27；D-04、D-07 | 不发布无法校验的场景 |
| Unity 映射 `unity_coordinate_mapping` | 业务平面、显示高度、转换精度和选点容差 | Unity 已选；映射待定；D-04、D-15 | 不以 Transform 作为规则位置，停止相关交互 |
| 动作集合 `action_policy_version` | 兵种、动作、对象资格、方案授权、互斥条件和终态 | PRD-28；D-01、D-04、D-06、D-09 | 未支持动作拒绝，不从源名称回退执行 |
| 队列政策 `command_queue_policy` | 草稿/采用区分、冲突、持续动作、阻塞、替换与去重 | PRD-28、32；D-03、D-07、D-09 | 不新增提交或覆盖已采用方案 |
| 执行记录 `execution_record_version` | 命令、运行、事件/损失、前后态和回执关联 | PRD-32、35；D-07、D-09 | 失败可定位；不能伪造完整审计 |
| 模型运行 `model_run_policy` | 模型/提示版本、角色预算、超时、重试、取消边界和工具白名单 | 原 AI 边界保留；增强待定；D-06、D-11 | 报告不可用或受阻，不生成替代成功结果 |
| 导入恢复 `import_compatibility_policy` | 格式、版本兼容、依赖、预览指纹、身份冲突与迁移规则 | PRD-34；D-07、D-09、D-10 | 不切换世界，不静默修复后开局 |
| 分析 `analysis_branch_policy` | 冻结来源、干预项、权限、结果身份及与主局关系 | 后续 P2；PRD-33；D-07、D-10 | 不创建可写主局结果 |
| 资源负载 `validation_workload_profile` | 导入规模、对象/报告数、快照大小、停止条件与实际耗时 | D-12；源项目数值不继承 | 报告当前处理限制，不能静默删单位或修改产品数量要求 |

每条参数记录类型、量纲、合法范围、空值含义、当前值或待定、版本、来源和确认记录。显示参数与规则参数分别登记；Unity 相机距离、绘制裁剪和特效品质不能进入规则计算或资源指令计数。

正式场景发布前，应固化场景、规则、地图资产、单位模板、转换政策和测试配置的版本关联。相同规则版本、相同初态和已采用动作应得到相同业务结果；内容哈希只能证明身份一致，不能代替权限、逻辑正确性或验收。
