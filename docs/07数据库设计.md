## 2. 数据建模原则

1. **当前权威状态只有一个入口。** `games` 指向当前有效分支与不可变快照。单位、编队、路线、探索、任务和资源在快照中按同一状态版本保存，不另建一套可以独立修改的当前单位表。
2. **关系表保护控制流程。** 对局、角色、命令、事件、存档、建议、人工处理、后台任务和知识索引使用关系表，承载唯一性、外键、幂等与检索条件。
3. **游戏事实与 UI 状态分开。** 相机位置、单位跟随、面板展开、鼠标拖动和临时输入不进入权威游戏快照；世界坐标、动作、观察与已采用计划必须保存。
4. **已提交快照与事实只追加。** 读档建立新分支并切换有效头，不覆盖旧快照、事件、已处理建议或历史结果。
5. **游戏快照与工作流检查点分别存储。** 二者显式关联；恢复某个 LangGraph 检查点不等于恢复游戏，不得重新执行已提交动作。
6. **身份与阵营需要持久化边界。** 同机三角色也不能由 URL 授权；保存角色席位和会话绑定，不扩展为用户中心或多人账号产品。
7. **版本与来源能追溯。** 场景、规则、原文、解析、向量模型、提示与模型配置保留版本；后续更新不能使历史结果或引用漂移。
8. **未知、空值与零分开。** 未配置参数和未知观察不能写成零；已耗尽资源的零是有效游戏值。测试参数始终保留测试标记。
9. **资料权限先过滤。** 主持人全局状态、红蓝私有输入、后台运行和引用不能通过列表、缓存或向量检索泄露给另一方。
10. **不把 JSON 当作无需约束的容器。** 快照与结构化建议有版本化结构及应用校验；关系、类型和可证明的唯一性尽量由数据库约束保护。
11. **持久化工作意图与业务提交一致。** 需要后续分析或解析时，在对应数据库事务中写入 `background_jobs`；数据库提交后由执行器领取，不能只在内存排队后就返回已接受。
12. **历史内容和当前执行资格分别保存。** 原运行、建议和引用可以保留，但读档、取消或恢复后必须重新核对执行世代与领取代次；保留历史不代表允许历史任务继续写回。

## 3. 关系概览

原首版基线建议二十张应用逻辑表，按下列职责分组；第十三节中的候选实体另按实际需求设计，不计为已批准的首版新增表。框架管理的 LangGraph 检查点表另计，不在本文伪造其内部结构。

| 分组 | 表名 | 关系 |
| --- | --- | --- |
| 规则与场景 | `rule_versions`、`scenario_versions` | 一个规则版本可供多个场景版本使用，已创建对局绑定固定版本 |
| 对局与角色 | `games`、`game_members`、`access_sessions` | 一局对应主持人、红方、蓝方三席位，每席位可有受控会话 |
| 分支与状态 | `game_branches`、`game_snapshots` | 一局多个历史分支，当前只激活一个分支和一个头快照 |
| 命令与历史 | `game_commands`、`game_events`、`game_saves` | 命令产生已提交状态及事件，存档引用完整快照 |
| AI 与决策 | `ai_runs`、`proposals`、`proposal_reviews`、`proposal_evidence` | 分析运行产生建议，人工处理与证据独立留痕 |
| 后台执行 | `background_jobs` | 持久化分析、解析与索引任务，记录领取代次和执行资格 |
| 资料与检索 | `knowledge_documents`、`document_versions`、`document_chunks`、`embedding_spaces`、`chunk_embeddings` | 原文按版本解析为片段，片段在明确向量空间内索引 |

二十表按组计数为 `2 + 3 + 2 + 3 + 4 + 1 + 5 = 20`。部署顺序按依赖拆分，不要求一次启用全部表：

| 实施批次 | 首次落地的数据职责 | 依赖与边界 |
| --- | --- | --- |
| B0／B1 | 前四组共十表：版本、对局席位、分支快照、命令事件及存档 | 足以承载确定性最小闭环；未启用的 AI 关联先不开放写入，不构造成功建议 |
| B3 | 四张 AI 表、`background_jobs` 及五张资料表 | 模型、原文、维度和检查点适配器确认后启用；与已存在核心表的关联用显式迁移补齐 |
| B4／B5 | 在既有表中完善四任务、恢复、历史与执行流程 | 不因增加任务模板而复制一套单位、评分或存档表 |

该顺序是本设计的实施建议；不能用尚未落地的后续表解释当前数据库能力。

```text
rule_versions ── scenario_versions ── games
                                      ├─ game_members ── access_sessions
                                      ├─ game_branches ── game_snapshots
                                      ├─ game_commands ── game_events
                                      ├─ game_saves ── 指向快照
                                      └─ ai_runs ── proposals
                                             │        ├─ proposal_reviews
                                      background_jobs └─ proposal_evidence
                                                            │
knowledge_documents ── document_versions ── document_chunks ──┘
                                                   │
embedding_spaces ───────────────────────── chunk_embeddings
```

关系图为概览，复合外键与跨分支例外见第七、八节。快照内的兵营、单位等使用稳定对象标识，但不因此建立逐对象逐步关系表；其引用完整性由状态结构校验和领域规则共同验证。

## 4. 通用字段与数据类型

### 4.1 共同字段与命名

下列二十张应用表均包含共同字段 `id UUID PRIMARY KEY` 和 `created_at TIMESTAMPTZ(3) NOT NULL`，后续字段表只列增量字段。UUID 由后端生成，不依赖额外数据库 UUID 扩展。可变记录另列 `updated_at`；快照、事件、人工处理和证据等不可变事实不提供通用修改入口。

未标“可空”的字段均为非空；“唯一”包括显式唯一约束或索引，不能仅靠代码查询。复合外键所引用的目标组合需建唯一约束，具体集合见第七节。数据库使用 UTF-8。

| 类别 | 建议类型 | 口径 |
| --- | --- | --- |
| 主键与关系标识 | `UUID` | 与中文名称、地图标签和可读业务编号分开 |
| 版本、提交序号、文件字节数 | `BIGINT` | 使用非负约束；内部计数不直接作为可见信息公开 |
| 仿真步 | `INTEGER` | 首版范围零至六十；同一步可发生多次人工处理，不能作为唯一状态键 |
| 数量、节点序号、执行代次 | `INTEGER` 或 `BIGINT` | 非负或正整数；不新增产品兵力上限 |
| 状态、阵营、方式 | `TEXT` 配合允许值约束 | 不使用难以演进的数据库枚举，变更允许值仍需迁移 |
| 结构化状态、输入与依据 | `JSONB` | 结构、必需键与语义由版本化校验器验证 |
| 业务十进制值 | JSON 中规范十进制字符串；必要关系字段使用 `NUMERIC` | 具体精度由规则版本明确，不套用人民币两位小数，也不把浮点误差当游戏规则 |
| 现实时间 | `TIMESTAMPTZ(3)` | 后端与数据库会话按 UTC 处理，API 带时区，页面按 Asia/Shanghai 显示 |
| 内容校验值 | `TEXT` 配合 `CHECK (字段 ~ '^[0-9a-f]{64}$')` | 小写十六进制 SHA-256；固定长度校验明确表达，不依赖 `CHAR` 补空格语义 |
| 向量 | pgvector 的 `vector` | 与向量空间及维度绑定，具体维度未定时不伪填 |
| 演示标记 | `BOOLEAN` | 对局、场景与资料均能明确区分测试内容 |

`TIMESTAMPTZ` 保存时间点，不保留原始时区名称；若展示需要，时区作为应用显示配置。仿真持续步数不用时间戳计算，程序暂停或关闭期间不按现实时间自动消耗游戏事件。

### 4.2 JSON 与完整性校验

提交前拒绝重复对象键、非有限数值、无效标识、结构缺失和未知的格式版本。`JSONB` 不能替代这些检查，也不保证字段顺序。

`payload_sha256` 等 JSON 校验值由后端对明确版本的规范化序列化结果计算，固定键排序、字符编码、数组顺序和十进制格式；保存 `hash_format_version`。不能依赖数据库 `jsonb::text` 的外观作为跨版本哈希协议。文件 `sha256` 则针对原始字节计算；文本片段与引用校验值针对所存文本的 UTF-8 字节计算，不临时裁剪空白或替换换行。文本预处理差异由解析版本表达，三种校验口径不混用。

`hash_format_version` 必须定义参与摘要的字段集合。快照摘要至少绑定状态载荷及影响解释的格式版本、场景与规则身份、仿真步和阶段；`snapshot_id`、新分支标识及落库时间是否参与必须明确，不能复制旧摘要后声称新封装已校验。恢复前验证来源，恢复后按目标格式重新生成摘要。摘要只能检查内容一致性，不能替代访问授权或证明原始内容可信。

### 4.3 JSON 字段边界与坐标版本

| 数据 | 关系表列承担 | JSON 承担 | 提交前校验 |
| --- | --- | --- | --- |
| 权威状态 | 归属、版本、步数、阶段、来源命令 | 单位、路线、观察、持有关系及冻结决策 | 对象 ID 唯一、跨集合引用、资源守恒、列与载荷一致 |
| 命令与建议 | 来源、权限关联、状态、依据、幂等键 | 判别联合参数、计划和诊断 | 按类型拒绝未知字段；客户端不能修改权限及可信来源 |
| 版本与发布 | 稳定身份、可用状态及校验值 | 规则、场景、解析和检索清单 | 必需字段与资源存在，已发布内容不可就地替换 |

应为对象型 JSON 增加 `jsonb_typeof(字段) = 'object'` 等本行类型检查；SQL `NULL`、JSON `null` 和空对象语义分别定义，不能互换。完整 Schema 和领域规则仍由版本化验证器承担，不新增 JSON 校验扩展。

当前 Unity 十二公里地图使用米制表现，演示状态仍保留旧业务坐标的映射。正式场景必须在 `definition` 中固定 `coordinate_system_id`、坐标单位、轴向、原点、范围及显示转换版本，快照通过 `manifest` 绑定。不得将旧样例坐标直接解释为米，或从 Unity 模型比例反推规则距离；历史样例继续保留其原格式与测试标记。

## 5. 对局、状态与存档表

### 5.1 `rule_versions`：不可变规则版本

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| `rule_code`、`version_label` | `TEXT` | 组合唯一，版本名称只用于识别 |
| `schema_version`、`hash_format_version` | `TEXT` | 规则结构与哈希协议版本 |
| `definition` | `JSONB` | 已确认规则、必需参数与单位定义；不保存可由模型执行的任意代码 |
| `payload_sha256` | `TEXT`，SHA-256 格式检查 | 规范内容校验值 |
| `availability` | `TEXT` | `draft`、`active`、`retired`；内容不可就地修改 |
| `is_demo` | `BOOLEAN` | 是否为明确的测试规则配置 |

规则内容变化新增版本。停用只影响未来选择，已有对局继续引用原版本；参数不完整的草稿不得用于正式开局。

### 5.2 `scenario_versions`：固定地图与场景版本

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| `scenario_code`、`version_label` | `TEXT`，组合唯一 | 一张固定虚构地图可有多个设计版本，不表示新增多地图玩法 |
| `rule_version_id` | `UUID` 外键 | 指向规则版本 |
| `schema_version`、`hash_format_version` | `TEXT` | 场景结构与哈希协议 |
| `definition` | `JSONB` | 地图范围与坐标系、道路、河流、高山、连接点、部署区、可飞和遮挡数据、任务模板与事件脚本 |
| `asset_manifest` | `JSONB` | 地图资源版本、受控资源标识和内容校验值，不保存开发电脑临时绝对路径 |
| `payload_sha256` | `TEXT`，SHA-256 格式检查 | 场景规范内容校验值 |
| `availability`、`is_demo` | `TEXT`、`BOOLEAN` | 可用状态与测试标记 |

内容与所绑定规则不可就地替换。图片纹理、Unity 显示高度与模型碰撞体不自动成为通行或交战规则。资产转换版本、组织模板、导航及公开表现资源由发布清单关联，场景加载不能混用不同发布内容。增加 `UNIQUE(id, rule_version_id)`，供对局以复合外键保证场景与规则匹配。

创建正式对局时，在同一版本绑定流程检查规则、场景及必要资源可用且非演示；任一依赖标为演示时，不得创建 `is_demo = false` 的对局。退役只阻止未来新建，已有局仍按绑定版本读取。三个布尔标记的关系属于跨表发布校验，不能用单表 CHECK 假装已全部保护。

### 5.3 `games`：对局及有效头指针

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| `game_no` | `TEXT` 唯一 | 可读编号，格式后续确定；内部关系使用 UUID |
| `title` | `TEXT` | 对局名称 |
| `creation_request_key` | `UUID` 唯一 | 创建请求的稳定标识，避免响应丢失后重复建局 |
| `creation_payload_sha256`、`creation_hash_format_version` | `TEXT`、`TEXT`，摘要执行 SHA-256 格式检查 | 创建输入摘要及其协议版本，同键不同输入应冲突 |
| `scenario_version_id`、`rule_version_id` | `UUID` 复合外键 | 指向匹配的场景及规则 |
| `active_branch_id` | `UUID` | 当前有效分支，必须属于本局 |
| `head_snapshot_id` | `UUID` | 当前有效快照，必须属于本局有效分支 |
| `control_revision` | `BIGINT`，大于等于零 | 对局控制修订；切换头、有效分支或运行控制时递增，不因轮询递增 |
| `execution_epoch` | `UUID` | 当前执行世代；创建、读档或受控恢复时由后端生成，历史任务不得据旧值写回 |
| `is_demo` | `BOOLEAN` | 对局演示标记 |
| `updated_at` | `TIMESTAMPTZ(3)` | 最近有效变更时间 |

不另存可以独立修改的 `current_step`、当前单位和最终分数。当前阶段与仿真步从头快照读取。创建对局时预生成本局、根分支和首快照标识，在同一事务内写入；头指针相关外键采用可延迟到提交时检查的方式，提交后不允许悬空指针。创建请求尚无既存对局时用 `creation_request_key` 去重，后续游戏操作使用命令表；创建入口调用资格及重试结果访问仍由服务端校验，不凭请求键发放角色权限。

`execution_epoch` 属于运行控制元数据，不是仿真步或世界状态，不从游戏存档恢复旧值。普通窗口刷新和普通工作进程重启不轮换世代；读档、备份恢复或明确撤销全局执行资格的受控恢复才轮换。备份恢复先隔离旧执行器，再生成新值、失效旧租约并完成对账；多服务实例不能各自在启动时改写世代。旧世代历史行保留，不对历史行设置必须等于当前世代的外键。

### 5.4 `game_members`：三角色席位

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| `game_id` | `UUID` 外键 | 所属对局 |
| `role` | `TEXT`，限 `host`、`red`、`blue` | 每局每角色唯一 |
| `display_name` | `TEXT` 可空 | 展示名称，不作为授权依据 |
| `updated_at` | `TIMESTAMPTZ(3)` | 席位展示信息更新时间 |

`UNIQUE(game_id, role)` 保证最多三个席位，服务端创建完整席位后才提供对应入口。角色记录不是操作系统账号，不引入密码、邮箱或用户管理字段。数据库不能仅凭这个唯一约束保证三席位均存在，创建事务还需完整性检查。

### 5.5 `access_sessions`：服务端会话绑定

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| `game_id`、`member_id` | `UUID` 复合外键 | 会话绑定本局某席位 |
| `token_digest` | `TEXT` 唯一，SHA-256 格式检查 | 后端生成的高熵不透明会话凭据的摘要，不存原始凭据 |
| `expires_at` | `TIMESTAMPTZ(3)` | 有效期，具体时长待 API 设计 |
| `revoked_at` | `TIMESTAMPTZ(3)` 可空 | 撤销时间 |

这张表服务于已确认的信息隔离，不表示新增登录页面。凭据生成、传递、恢复与浏览器存放方式在 API 阶段确定；禁止从 `?role=`、请求中的成员编号或展示名称直接建立信任。

### 5.6 `game_branches`：读档分支与来源

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| `game_id` | `UUID` 外键 | 所属对局 |
| `parent_branch_id`、`fork_snapshot_id` | `UUID`，成对可空 | 根分支均为空；读档分支指向本局父分支及其来源快照 |
| `created_by_command_id` | `UUID` 可空 | 创建根分支可为空，读档分支关联已核对的读档命令 |

父分支与来源快照必须属于同一对局，来源快照必须属于所指父分支；创建后不可修改。分支“当前是否有效”由 `games.active_branch_id` 唯一决定，不再保存另一套可相互矛盾的 active 标志。

### 5.7 `game_snapshots`：完整、不可变状态

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| `game_id`、`branch_id` | `UUID` 复合外键 | 所属对局与分支 |
| `revision` | `BIGINT`，大于等于零 | 分支内提交修订；`UNIQUE(game_id, branch_id, revision)` |
| `world_revision` | `BIGINT`，大于等于零 | 本分支内影响游戏决策依据的领域状态版本，口径见第八节 |
| `simulation_step` | `INTEGER`，零至六十 | 仿真分钟，同一步可存在多个修订 |
| `phase` | `TEXT` | `preparing`、`running`、`paused`、`awaiting_confirmation`、`finished`；与载荷一致 |
| `snapshot_kind` | `TEXT` | `initial`、`command`、`fork`、`final` |
| `schema_version`、`hash_format_version` | `TEXT` | 快照结构与哈希版本 |
| `state_payload` | `JSONB` | 完整权威游戏状态，内容见下表 |
| `payload_sha256` | `TEXT`，SHA-256 格式检查 | 规范载荷校验值 |
| `source_command_id` | `UUID` 可空 | 产生本快照的命令；根初始状态可为空 |

载荷至少包含以下字段组，具体属性定义由 JSON 结构契约和规则版本约束。所有对象集合用稳定标识关联，不用列表位置作唯一键。

| 载荷字段组 | 必须保存的内容 | 关键校验 |
| --- | --- | --- |
| `manifest` | 场景、规则、快照格式与必要运行参数版本 | 与所属对局绑定一致 |
| `lifecycle` | 仿真步、阶段、暂停原因、双方准备状态 | 与快照列一致；等待确认不能继续推进 |
| `camps` | 双方兵营占地、出入口、停靠点与补给功能 | 每方一个合法兵营，开始后位置不变 |
| `units` | 类型、阵营、兵营、编队、位置、动作、主任务、耐久、能源与补给 | 单位标识唯一，所属对象存在，资源与状态符合规则 |
| `formations` | 成员、任务、节点分工、依赖与受阻原因 | 一个单位至多一个活动编队和主任务 |
| `tasks` | 四类模板实例、目标修订、节点、截止步及终结原因 | 旧目标留痕，新目标从零；节点不凭插画完成 |
| `routes` | 道路或空中移动类型、点段、合法性与行进进度 | 引用有效单位和地图连接；不保存屏幕像素路线 |
| `observations` | 红蓝独立探索、报告、来源、最后有效位置与时间 | 历史与当前信息分开，失视不继续实时更新 |
| `logistics` | 库存、服务占用、物资与受损设备的唯一持有者 | 同一对象只有一个持有者，同次服务不重复恢复 |
| `conditions` | 脚本、已触发实例、开始及恢复步、影响对象和处理状态 | 同一脚本实例只生效一次；持续时间按仿真步 |
| `decisions` | 分析待处理请求、已有建议标识、冻结内容与已采用计划、必要处理事实 | 尚无真实建议时只保存等待状态，不伪填建议；历史显示不依赖建议表后来状态 |
| `scores` | 分项、权重、指令计数、独立安全损失标识、总分及结束结果 | 规则版本固定，同一损失不重复扣分，最终结果冻结 |

首版建议每次权威提交保存完整快照，避免首版必须重放所有事件才能恢复。大量单位下的存储放大需要测试；以后可分段或压缩，但必须维持完整逻辑快照及校验边界，不在本阶段承诺无限规模性能。

### 5.8 `game_commands`：变更命令与幂等结果

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| `game_id`、`origin_branch_id` | `UUID` 复合外键 | 请求进入时的上下文，读档后不重写为新分支 |
| `actor_member_id` | `UUID`，与 `game_id` 复合外键 | 提交者席位；系统推进也必须关联有效的主持人控制授权 |
| `request_key` | `UUID` | 对齐现有接口的 UUID 幂等键；由客户端或受控执行器为一次逻辑操作生成 |
| `request_hash`、`hash_format_version` | `TEXT`、`TEXT`，摘要执行 SHA-256 格式检查 | 输入摘要，含类型及原始有效业务参数 |
| `command_type` | `TEXT` | 配置、开局、推进、暂停、确认、事件、保存、读档等受控命令 |
| `expected_control_revision` | `BIGINT`，非负 | 请求依据的对局控制版本 |
| `base_snapshot_id` | `UUID` | 属于请求进入时本局、本分支的依据快照 |
| `request_payload` | `JSONB` | 原始有效参数，不含会话密钥 |
| `source_kind` | `TEXT` | `human`、`workflow`、`scheduler`；未来单位 Agent 需单独扩展允许值和授权规则 |
| `source_ai_run_id`、`source_proposal_id` | `UUID` 可空 | 可信来源运行或已采用建议；采用同局复合外键，运行方别、来源分支和采用资格再由服务核验 |
| `execution_epoch` | `UUID` | 受理时的执行世代；历史结果允许查询，新执行必须匹配当前世代 |
| `status` | `TEXT` | `accepted`、`running`、`succeeded`、`rejected`、`failed` |
| `result_branch_id`、`result_snapshot_id` | `UUID`，成对可空 | 结果所属分支与快照；读档结果可处于新分支 |
| `result_payload`、`error_payload` | `JSONB` 可空 | 已核对结果或错误，不直接作为跨角色响应缓存 |
| `completed_at`、`updated_at` | `TIMESTAMPTZ(3)`，完成时间可空 | 执行时间 |

`UNIQUE(game_id, origin_branch_id, actor_member_id, request_key)` 保护重试。同键不同输入冲突，同键同输入返回已有处理结果；先校验当前请求有权核对该命令，再查幂等结果。读档成功后，用原请求重试应查询原命令结果，不再次恢复。

请求摘要覆盖 `command_type`、`game_id`、原分支、`base_snapshot_id`、服务端解析后的原控制版本及有效业务参数，摘要规则固定版本。令牌、签名后的 `context_token` 字符串、接收时间和重试次数不作为业务参数；更换会话后仍须证明是原席位，不能以新令牌为由生成另一条命令。相同键重试先核对已有摘要，再检查是否需要新执行；旧结果查询不要求原分支仍有效。

短命令在同一事务内形成最终结果；`accepted/running` 只用于已有持久化后续任务的异步命令。`workflow` 来源必须有关联运行，`scheduler` 必须持有受控的主持人推进授权；`actor_member_id` 表达授权席位，`source_kind` 表达执行来源，两者不能互相替代。模型不得自己填写这些字段。

`result_snapshot_id` 不能错误地限制为原分支快照，需与 `result_branch_id` 做本局复合外键。只查询或存档可引用未改变的头快照；成功命令结果不一定产生新游戏修订。

### 5.9 `game_events`：已发生事实与计分依据

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| `game_id`、`branch_id`、`snapshot_id` | `UUID` 复合外键 | 该事实提交后的所属快照 |
| `command_id` | `UUID` | 产生事实的本局命令；读档命令可来自父分支 |
| `snapshot_revision` | `BIGINT`，大于等于零 | 提交快照的分支修订；以包含修订的复合外键绑定，供稳定排序与游标使用 |
| `event_index` | `INTEGER`，大于等于零 | 同一快照内排序，组合唯一 |
| `fact_key` | `TEXT` | 分支内稳定事实键，组合唯一，区别同类但独立发生的事件 |
| `event_type` | `TEXT` | 任务节点、交接、事件注入或恢复、方案处理、安全损失等 |
| `simulation_step` | `INTEGER`，零至六十 | 发生仿真时间 |
| `visibility` | `TEXT` | `public`、`red`、`blue`、`host`，仅为粗筛标记 |
| `payload` | `JSONB` | 事实、参与对象及必要前后值，由应用校验与权限投影 |

使用 `UNIQUE(snapshot_id, event_index)` 与 `UNIQUE(game_id, branch_id, fact_key)`。`snapshot_revision` 是不可独立修改的查询冗余列，与 `snapshot_id` 一起引用快照，不维护第二套游戏修订。可见标记不能替代对象发现和字段权限检查，公共事件不夹带私有部队信息。单次损失事实在快照内保存已计数标识，分支继承时不再次扣分。

事件不作为第二套可直接改写当前状态的源。快照用于恢复完整状态，事件解释其变化；同事务提交确保对应事实与快照不会各成功一半。时间线排序关联快照的分支修订及 `event_index`，不按 UUID 字面值或毫秒时间推测同一步提交顺序。

### 5.10 `game_saves`：自动、手动与结束存档入口

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| `game_id`、`branch_id`、`snapshot_id` | `UUID` 复合外键 | 指向完整、已提交的本局快照 |
| `save_kind` | `TEXT` | `auto`、`manual`、`final` |
| `display_name` | `TEXT` 可空 | 名称与覆盖规则仍待确认，不以名称作为唯一键 |
| `created_by_member_id` | `UUID`，本局复合外键，可空 | 手动必须是主持人；自动或结束保存可为空 |
| `source_command_id` | `UUID`，本局外键，可空 | 对应保存、推进或其他触发命令；仅创建对局时的初始自动入口可无命令 |
| `updated_at` | `TIMESTAMPTZ(3)` | 自动入口更新时的现实时间 |

建议每分支保留一个可更新的最近自动存档入口和一个结束入口，分别用条件唯一索引保护；所有历史快照仍不可变。手动存档新增多条记录，不默认覆盖，不擅自规定槽数。更新自动入口不是删除之前的状态。

一个 `create_save` 或存档退出命令最多创建一个手动入口，以 `source_command_id` 在 `save_kind = 'manual'` 范围内唯一保护。重复点击重用原请求键，不能以“再查一次名称”去重；不同命令允许保存同一快照并使用相同展示名称。自动入口可更新 `snapshot_id`、来源命令及 `updated_at`，`created_at` 保留首次创建时间。

手动及结束入口必须关联来源命令；初始自动入口的空来源只能由创建事务产生，服务核对它确实指向本局根初始快照。后续自动入口更新必须记录实际触发命令，不能用空来源绕过来源追踪。

列表保存步数从所指快照取得，不另存易失配的步数。只有成功事务中的入口才能显示可恢复；已结束对局按既定规则只读，不能借存档入口擅自重开已结束游戏。

## 6. AI、工作流与知识资料表

### 6.1 `ai_runs`：分析运行与工作流关联

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| `game_id`、`branch_id`、`base_snapshot_id` | `UUID` 复合外键 | 分析依据的本局分支快照 |
| `side` | `TEXT`，限 `red`、`blue` | 不用主持人全局输入替代本方输入 |
| `execution_epoch` | `UUID` | 分析发起时的执行世代，写回时与当前对局及执行任务一并核对 |
| `agent_role` | `TEXT` | 总指挥、侦察、陆兵、保障四种逻辑角色 |
| `input_view`、`model_manifest`、`knowledge_manifest` | `JSONB` | 实际允许输入、模型与提示配置版本、使用资料及检索版本；不含模型密钥 |
| `input_view_sha256`、`hash_format_version` | `TEXT`、`TEXT`，摘要执行 SHA-256 格式检查 | 本方结构化输入指纹，排除无关 UI 与调试字段 |
| `checkpoint_thread_id` | `TEXT` 唯一 | 工作流命名空间与当前运行绑定，不能跨阵营或读档分支复用 |
| `checkpoint_ref` | `JSONB` 可空 | 适配器提供的检查点引用，不假造框架内部主键 |
| `status` | `TEXT` | `queued`、`running`、`waiting_human`、`succeeded`、`failed`、`stale`、`cancelled` |
| `output_payload`、`error_payload`、`usage` | `JSONB` 可空 | 模型输出、失败和实际调用量；未知费用不填零 |
| `started_at`、`finished_at`、`updated_at` | `TIMESTAMPTZ(3)`，前两项可空 | 运行时间 |

未来单位 Agent 如启用，应通过受控绑定引用区分单位会话与四个逻辑角色，不将单位 ID 拼入 `agent_role` 或无版本扩展允许值。实际输入按权限保留用于追溯，不能向另一方提供；变化的主持人隐藏状态不得被重新注入本方输入。检查点物理表采用选定持久化适配器的正式迁移，建议与应用表使用独立受控 schema 或前缀，具体配置在包选型时核对。

### 6.2 `proposals`：结构化建议

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| `game_id`、`branch_id`、`base_snapshot_id` | `UUID` 复合外键 | 本建议的有效上下文与原始依据 |
| `side` | `TEXT`，限 `red`、`blue` | 所属方 |
| `execution_epoch` | `UUID` | 本建议可被处理的执行世代；跨恢复必须建立新记录并重新校验 |
| `ai_run_id` | `UUID` 可空 | 原生成运行，存在时必须同局、同分支、同方 |
| `source_proposal_id` | `UUID`，同局外键，可空 | 读档恢复产生的新建议关联原建议，不修改原建议 |
| `proposal_kind`、`status` | `TEXT` | 首次、重大调整等种类与生命周期，允许值见第七节 |
| `requires_confirmation` | `BOOLEAN` | 由既定规则决定，不由模型自行声明；非重大调整也须通过规则采用入口 |
| `schema_version` | `TEXT` | 结构化建议格式 |
| `content_payload`、`validation_payload` | `JSONB` | 原建议、单位分工、资源变化、未知项与校验结果 |
| `based_on_world_revision` | `BIGINT`，非负 | 原依据领域版本，采用仍需检查本方输入及最新规则 |
| `input_view_sha256`、`hash_format_version` | `TEXT`、`TEXT`，摘要执行 SHA-256 格式检查 | 对应实际允许信息的指纹 |
| `updated_at` | `TIMESTAMPTZ(3)` | 生命周期更新时间 |

`ai_run_id` 与 `source_proposal_id` 至少一项存在。原建议内容不可就地编辑，人工修改写入处理记录；生命周期可变但不能据后来状态改写历史快照。读档后的待处理建议创建新分支记录，保留来源与证据，不让旧分支建议继续执行。要求确认的建议只有最终人工处理与采用事务成功后才能进入已采用状态；非重大方案允许按既定规则直接采用并记录命令，不制造不存在的人工处理。

### 6.3 `proposal_reviews`：人工处理与采用事实

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| `game_id`、`branch_id`、`proposal_id` | `UUID` 复合外键 | 所处理的本局分支建议 |
| `reviewer_member_id` | `UUID`，本局外键 | 必须为该建议所属方操作员，服务层检查 |
| `decision` | `TEXT` | `approve`、`modify_approve`、`reject` |
| `submitted_changes` | `JSONB` | 人工修改，未修改时为空对象，只含允许的分工、优先级与额度 |
| `adopted_plan` | `JSONB` 可空 | 批准时保存实际采用计划，驳回时为空 |
| `command_id` | `UUID`，本局外键 | 人工处理的幂等命令 |
| `result_snapshot_id` | `UUID`，本局本分支外键 | 本次处理后的完整状态 |

`UNIQUE(proposal_id)` 保证同一建议只有一次最终人工处理。输入校验失败不写入最终处理表，可由命令错误记录诊断；用户修正后仍可提交。驳回后若重新生成建议，使用新建议标识。人工确认、采用计划、状态快照与事实在一个事务中提交。

### 6.4 `proposal_evidence`：文档、报告与规则证据

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| `game_id`、`proposal_id` | `UUID` 复合外键 | 所属建议及对局 |
| `position` | `INTEGER`，大于等于零 | 建议内顺序，组合唯一 |
| `source_type` | `TEXT` | `document`、`report`、`rule` |
| `document_version_id`、`chunk_id` | `UUID` 可空 | 文档版本与可选片段；片段存在时必须属于该版本 |
| `observation_snapshot_id`、`report_object_id` | `UUID`、`TEXT`，可空 | 报告所在本局快照及 JSON 内稳定报告标识 |
| `rule_version_id` | `UUID` 可空 | 规则来源 |
| `locator` | `JSONB` | 页、章节、段落或报告有效步等原文定位 |
| `excerpt`、`excerpt_sha256` | `TEXT`、`TEXT`，摘要执行 SHA-256 格式检查 | 已采用引用的冻结片段与文本校验值 |
| `source_manifest` | `JSONB` | 冻结引用时的资料标题、版本、解析代次或规则／报告版本和定位格式；不保存临时下载地址或密钥 |

按来源类型检查必需字段，未使用的来源列为空。文档必须有版本，报告必须有快照和报告标识，规则必须有规则版本。外键保护关系，快照内报告存在性与当时本方可见性由应用检查。`UNIQUE(proposal_id, position)` 防止显示顺序冲突。

复合文档引用采用 `(document_version_id, chunk_id)`，其中版本非空、片段可空；`source_type` 的本行互斥检查必须补齐。冻结摘录不替代原文校验：提交时核对片段内容摘要、定位范围与授权。`source_manifest` 保存的是可追溯展示元数据，不复制一份可修改的资料权限；读取和下载仍检查当前访问资格。

### 6.5 `background_jobs`：持久化任务与执行资格

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| `job_type`、`subject_key` | `TEXT` | 分析、解析、索引等任务类型与稳定目标键 |
| `game_id`、`branch_id` | `UUID`，成对可空 | 对局任务绑定分支；全局资料任务可为空 |
| `ai_run_id` | `UUID` 可空 | 分析任务关联运行；存在时与任务对局分支一致 |
| `command_id` | `UUID` 可空 | 异步命令的持久化执行关联；非命令任务为空，存在时必须同局 |
| `execution_epoch` | `UUID` 可空 | 对局任务必填，全局资料任务为空；不得沿用已失效世代 |
| `document_version_id` | `UUID` 可空 | 资料处理目标；不同任务类型按结构检查目标 |
| `target_parse_revision`、`target_processing_generation` | `INTEGER`、`BIGINT` 可空 | 资料任务冻结目标解析代次及处理代次，防止旧解析或索引任务覆盖新发布 |
| `status` | `TEXT` | `queued`、`running`、`waiting_retry`、`waiting_human`、`succeeded`、`failed`、`cancelled` |
| `payload`、`result_payload`、`error_payload` | `JSONB`，后两项可空 | 任务输入和结果，不保留明文凭证 |
| `attempt_count`、`claim_generation` | `INTEGER`、`BIGINT`，非负 | 执行次数与领取代次，领取代次只能递增 |
| `lease_owner`、`lease_until` | `TEXT`、`TIMESTAMPTZ(3)`，可空 | 当前执行归属和租约截止；运行中必需 |
| `available_at` | `TIMESTAMPTZ(3)` | 最早可领取现实时间，不是仿真时间 |
| `updated_at` | `TIMESTAMPTZ(3)` | 任务状态更新时间 |

使用条件唯一索引限制同一 `job_type, subject_key` 的活动任务，活动状态包含排队、执行、待重试和待人工；等待人工不占工作线程或数据库锁。`subject_key` 必须由服务端按固定格式生成并包含完整作用域，例如运行 ID，或文档版本、解析代次、向量空间和处理代次，不能只用文件名、角色名或客户端自由输入。是否存在同目标历史完成任务不阻止显式新运行，但同一分析运行的重复入队必须核对。

提交结果须同时匹配任务标识、执行归属、领取代次、有效状态和未过期租约；对局任务另匹配执行世代、当前分支和领域依据，资料任务另匹配目标处理代次。资格检查和结果写入在同一事务内，受影响行数必须为一；不能先查询资格、释放事务，再无条件保存结果。租约过期不等于旧线程自动停止，回收任务时更新代次使旧执行者失去提交资格。具体租约时长和重试上限仍待实施确定。

### 6.6 `knowledge_documents`：资料逻辑身份

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| `document_code` | `TEXT` 唯一 | 稳定资料标识，不与文件名绑定 |
| `title` | `TEXT` | 资料展示名称 |
| `source_description` | `TEXT` 可空 | 来源说明，不替代版本级原文定位 |
| `is_demo`、`updated_at` | `BOOLEAN`、`TIMESTAMPTZ(3)` | 演示标记与元数据更新时间 |

不以逻辑文档当前名称或某个“最新版本”替换历史引用。标题和列表本身也按可访问版本过滤，私有文档存在性不向无权方公开。

### 6.7 `document_versions`：原文版本与索引发布状态

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| `document_id` | `UUID` 外键 | 所属逻辑资料 |
| `version_label` | `TEXT` | 同文档内唯一 |
| `storage_key`、`original_filename`、`media_type` | `TEXT` | 受控存储键、原始名称与类型；存储键唯一 |
| `size_bytes`、`sha256` | `BIGINT` 非负、`TEXT`，摘要执行 SHA-256 格式检查 | 原始字节大小和校验值 |
| `scope_game_id` | `UUID` 可空 | 私有资料必须绑定对局；为空时仅允许共享资料 |
| `visibility` | `TEXT` | `shared`、`red`、`blue`、`host` |
| `file_status`、`parse_status`、`review_status`、`retrieval_status` | `TEXT` | 原文、解析、审核、可检索状态分别保存 |
| `active_parse_revision` | `INTEGER` 可空，存在时大于零 | 当前成功发布的解析代次，未成功时为空 |
| `next_parse_revision` | `INTEGER`，大于零 | 下次可分配解析代次；锁定文档版本行后分配并递增，不复用失败代次 |
| `processing_generation` | `BIGINT`，非负 | 重建、取消或接管处理流程时递增，旧任务不能发布 |
| `parser_manifest` | `JSONB` | 当前已发布解析代次的解析器、配置、分块和中文词法版本；构建新代次时不提前覆盖 |
| `retrieval_manifest` | `JSONB` 可空 | 已发布检索集合：解析代次、词法配置、可用向量空间、内容集合摘要及发布修订 |
| `publication_revision` | `BIGINT`，非负 | 成功发布或撤销检索资格时递增，供并发检查和检索缓存失效使用 |
| `is_demo`、`updated_at` | `BOOLEAN`、`TIMESTAMPTZ(3)` | 测试标记与处理状态时间 |

原始文件、校验值与版本身份不可变，替换文件新增版本。处理状态可变；发布可检索前检查文件可读、解析与审核满足条件、对应索引就绪。对局私有资料的跨局复用不得默认开启，主持人可见也不等于双方模型可检索。

`parse_status` 描述最近一次处理尝试，不能单独判定旧发布是否可用。重解析期间可继续使用仍完整、已审核且未撤销的旧发布；失败不清空旧 `active_parse_revision`。无旧发布时，构建或失败都不可检索。`retrieval_status = 'ready'` 专指发布清单可用，不代表所有候选模型与未来索引都已建好；撤销审核、原文缺失或主动停用时立即撤销检索资格。

### 6.8 `document_chunks`：解析片段与原文位置

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| `document_version_id` | `UUID` 外键 | 来源原文版本 |
| `parse_revision`、`ordinal` | `INTEGER`，前者大于零，后者非负 | 解析代次与片段顺序，三列组合唯一 |
| `parent_chunk_id` | `UUID` 可空 | 父章节，须同文档版本、同解析代次 |
| `section_path`、`locator` | `JSONB` | 章节层级、页码和段落位置；缺失页码不伪造 |
| `content`、`content_sha256` | `TEXT`、`TEXT`，摘要执行 SHA-256 格式检查 | 片段原文与文本校验值 |
| `parser_manifest`、`parser_manifest_sha256` | `JSONB`、`TEXT`，摘要执行 SHA-256 格式检查 | 本解析代次的冻结配置及摘要；同代次各片段必须一致，避免历史解析配置被当前版本覆盖 |
| `lexical_terms` | `TSVECTOR` 可空 | 经选定中文处理流程产生的词法数据，不预设默认配置满足中文 |

片段发布后不可就地改写；重新解析新增代次，完整后原子更新 `active_parse_revision`。旧引用仍指向旧代次片段，不能因重建索引删除。父子关系用复合外键，循环与层级有效性在导入校验中检查。

在保持二十表的前提下，解析配置随片段保存，允许同代次重复存放这一小段不可变元数据；一致性由发布事务检查。只有确有解析任务级查询和规模证据时，才另行评审是否拆出解析版本表，本轮不新增该表。

### 6.9 `embedding_spaces`：向量空间定义

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| `space_code` | `TEXT` 唯一 | 向量空间稳定标识 |
| `provider_code`、`model_name`、`model_revision` | `TEXT` | 供应方、模型及确定的版本，不含访问密钥 |
| `dimension` | `INTEGER`，大于零 | 实际验证后的维度，不填未经选型的默认数值 |
| `distance_metric` | `TEXT` | 选定度量方式，与查询和索引操作符一致 |
| `preprocessing_manifest` | `JSONB` | 文本预处理、归一化和向量化配置 |
| `availability` | `TEXT` | 活跃或停用等状态，不改变空间内容 |

模型、维度、度量或预处理空间变化新增记录，不就地改写。添加 `UNIQUE(id, dimension)` 供嵌入记录验证维度。不能仅凭模型名称相同认定两个向量空间兼容。

### 6.10 `chunk_embeddings`：片段向量

| 字段 | 类型与约束 | 说明 |
| --- | --- | --- |
| `chunk_id` | `UUID` 外键 | 被向量化的不可变片段 |
| `embedding_space_id`、`dimension` | `UUID`、`INTEGER`，复合外键 | 关联向量空间及其维度 |
| `embedding` | `vector` | 扩展向量类型，检查 `vector_dims(embedding) = dimension` |
| `source_content_sha256` | `TEXT`，SHA-256 格式检查 | 原始片段校验值，与 `chunk_id` 共同引用 `document_chunks(id, content_sha256)`；空间清单另定义向量化预处理 |

`UNIQUE(chunk_id, embedding_space_id)` 防止同一空间重复嵌入。未就绪向量不写入成功记录；部分索引失败保留可诊断任务，不将整个版本标为已完成。初期可在过滤后的集合进行精确检索，规模需要时再为固定空间与固定维度建立相匹配的表达式／条件索引，不在混合维度列上直接建一个通用近似索引。

数据库复合外键保证记录声明的原始片段摘要匹配，应用另核对实际送入模型的文本及空间预处理；外键不能证明某个向量确实由该模型计算。向量的维度、元素有限性和所选度量的合法性均需验证；使用余弦距离时拒绝零范数向量，并验证查询向量使用同一空间。

## 7. 约束、索引与删除策略

### 7.1 主键、外键与同局约束

| 对象 | 必须落实的约束 |
| --- | --- |
| 场景与规则 | 场景版本的 `(id, rule_version_id)` 唯一，对局以复合外键引用匹配版本 |
| 同局对象 | `game_members`、`game_branches`、`game_snapshots`、`game_commands`、`proposals` 增加 `(game_id, id)` 唯一，供同局外键使用 |
| 同分支对象 | `game_snapshots`、`ai_runs`、`proposals` 增加 `(game_id, branch_id, id)` 唯一，防止跨局跨分支引用 |
| 事件修订 | `game_snapshots` 增加 `(game_id, branch_id, id, revision)` 唯一；事件的 `(game_id, branch_id, snapshot_id, snapshot_revision)` 引用该组合 |
| 当前有效头 | `games(id, active_branch_id)` 引用分支；`games(id, active_branch_id, head_snapshot_id)` 引用快照，相关循环引用使用可延迟外键 |
| 分支来源 | `(game_id, parent_branch_id, fork_snapshot_id)` 引用父分支快照；父分支与来源成对空或成对存在 |
| 命令依据与结果 | 原依据引用原分支快照；结果引用本局结果分支快照；读档允许结果分支不同，不能使用错误的原分支外键 |
| 事件 | 事件快照与本局分支一致，命令同局；`event_index` 和 `fact_key` 分别唯一 |
| 建议与处理 | 分析表额外提供 `(game_id, branch_id, side, id)` 唯一，建议据此关联同局同方同分支分析；人工处理与建议同分支，处理者同局且方别经应用验证 |
| 恢复建议来源 | `proposals` 增加 `(game_id, side, id)` 唯一；来源建议允许来自父历史分支但必须同局同方，应用检查属于分叉前缀并拒绝自引用 |
| 会话与存档 | 会话 `(game_id, member_id)` 引用席位；存档 `(game_id, branch_id, snapshot_id)` 引用快照，来源命令与创建者均同局 |
| 异步任务 | 对局任务 `(game_id, branch_id)` 引用分支；运行关联引用 `(game_id, branch_id, id)`，命令关联引用 `(game_id, id)`，资料关联引用文档版本；按任务类型检查互斥目标 |
| 文档片段 | `(document_version_id, parse_revision, ordinal)` 唯一；父片段通过唯一组合 `(document_version_id, parse_revision, id)` 关联 |
| 文档引用 | `document_chunks(document_version_id, id)` 唯一，证据同时指定版本和片段时使用复合外键 |
| 向量 | 空间与维度复合外键、片段与空间唯一、向量维度检查；片段增加 `(id, content_sha256)` 唯一，嵌入记录以片段与源摘要复合外键引用 |

复合外键中的 `game_id` 等作用域列保持非空；可选目标标识为空时明确表示没有该关联，可采用默认 `MATCH SIMPLE`。目标标识非空时作用域不能为空。父分支与来源快照、命令结果分支与结果快照等互依赖可空列额外检查成对为空或同时存在，不能因部分为空跳过必要保护。数据库 `CHECK` 用于本行条件，不声称可以直接检查其他行或 JSON 对象的跨集合业务关系；这些由外键、事务、必要约束触发器或应用完整性校验承担。

外键引用的主键／唯一约束使用非延迟约束；不能拿条件唯一索引充当普通外键目标。允许延迟的是循环关系的外键检查，例如 `games` 指向初始分支和快照、快照回指来源命令、分支回指读档命令，使用 `DEFERRABLE INITIALLY DEFERRED` 并在同一事务内补齐。存在可延迟检查时使用 `ON DELETE NO ACTION`，不将不可延迟的删除限制误写成同一行为。

`game_id` 非空而目标标识可空的复合关联继续采用 `MATCH SIMPLE` 加显式本行检查；不能直接换成要求全部为空的 `MATCH FULL`，否则合法的无来源根记录也无法插入。完整性目标和实际外键声明必须逐一对应。

快照内对象引用、任务能力、补给守恒、方别资格、文档审核发布条件和无循环分支等仍需应用校验。分支只允许引用已存在且属于来源历史的父快照，禁止任意改写父关系。

### 7.2 状态值与本行检查

以下是首版建议的数据库允许值，在迁移与应用类型中统一维护；中文标签由显示层映射。状态允许值并不授权任意跳转，转换仍由应用流程检查。

| 字段或表 | 允许值或本行检查 |
| --- | --- |
| 规则、场景 `availability` | `draft`、`active`、`retired` |
| 建议 `proposal_kind` | `initial`、`major_adjustment`、`routine_adjustment`、`restored` |
| 建议 `status` | `draft`、`ready`、`pending_review`、`adopted`、`rejected`、`stale`、`cancelled` |
| 向量空间 `availability` | `active`、`retired` |
| 向量空间 `distance_metric` | `cosine`、`l2`、`inner_product`，选定空间只使用其中一种 |
| 原文 `file_status` | `writing`、`ready`、`failed`、`missing` |
| 原文 `parse_status` | `pending`、`parsing`、`ready`、`failed` |
| 原文 `review_status` | `pending`、`approved`、`rejected` |
| 原文 `retrieval_status` | `pending`、`building`、`ready`、`failed`、`disabled` |
| 私有资料 | `scope_game_id` 为空时 `visibility` 必须为 `shared` |
| 会话 | `expires_at > created_at`，非空凭据摘要；撤销与过期均由请求入口检查 |
| 任务租约 | `running` 时归属与截止时间非空，其余状态清除执行租约；等待人工不持有租约 |
| 命令终态 | `succeeded/rejected/failed` 时 `completed_at` 非空，其余为空；成功必须有成对结果分支／快照，失败不产生新的成功状态 |
| 命令结果 | 成功时 `result_payload` 为对象且 `error_payload` 为空；拒绝或失败时 `error_payload` 为对象，不能同时宣称成功 |
| 任务目标 | 对局任务的局、分支、执行世代同时存在；全局资料任务三项均空且文档及目标代次必填；运行、命令关联不得缺少对局作用域 |
| 资料发布 | `next_parse_revision > 0`、处理与发布修订非负；存在活动解析时 `next_parse_revision > active_parse_revision`；`retrieval_status = 'ready'` 时活动解析及发布清单非空 |
| 证据来源 | 文档／报告／规则必需列分别存在，其余来源列为空；报告标识不得为空字符串 |
| 人工处理 | `reject` 时 `adopted_plan` 为空，批准时非空；合法角色仍需跨表检查 |
| 存档来源 | `manual/final` 的来源命令非空；手动创建者非空且必须为主持人，初始自动存档例外由创建事务核对 |
| 内容标识 | SHA-256 字段为六十四位十六进制；计数、序号和大小按各字段约束非负或为正 |

已在各表列出的角色、阵营、命令、任务、快照、来源与处理允许值也需要对应 CHECK。`command_type`、`event_type` 和 `job_type` 的完整代码字典随 API 与规则契约锁定；在代码字典确认前不能将任意字符串接入执行器。`agent_role` 建议统一为 `commander`、`recon`、`ground`、`support`。

### 7.3 查询与领取索引

| 查询 | 建议索引 |
| --- | --- |
| 对局列表 | `games(created_at, id)`；演示筛选按实际查询再加组合索引 |
| 席位与会话 | `(game_id, role)` 唯一、`token_digest` 唯一、会话 `member_id` 索引 |
| 分支快照 | `(game_id, branch_id, revision)` 唯一；`(game_id, branch_id, simulation_step, revision)` 支持同一步修订查找 |
| 幂等与处理中命令 | 原分支与成员请求键唯一；`(game_id, status, created_at)` 支持核对 |
| 时间线 | `(game_id, branch_id, snapshot_revision, event_index)`；按步筛选先查询快照修订范围，不能按随机 `snapshot_id` 排序 |
| 存档列表 | `(game_id, created_at, id)`；`auto` 和 `final` 分别按 `(game_id, branch_id)` 条件唯一 |
| 建议与运行 | `(game_id, branch_id, side, status, created_at)`；处理表 `proposal_id` 唯一 |
| 后台领取 | 在可领取状态上建立 `(available_at, created_at, id)` 条件索引；运行租约到期查询单独索引 |
| 活动任务去重 | 对 `queued/running/waiting_retry/waiting_human` 建 `(job_type, subject_key)` 条件唯一索引 |
| 异步命令执行 | 在 `command_id IS NOT NULL` 范围内对 `(command_id)` 条件唯一；一个异步命令对应一个可恢复执行任务，内部阶段通过该任务状态推进 |
| 手动存档幂等 | `save_kind = 'manual'` 范围内 `source_command_id` 条件唯一；自动与结束入口仍按分支分别唯一 |
| 版本与片段 | `(document_id, version_label)` 唯一；片段代次及顺序唯一；资料过滤组合按实际查询验证 |
| 词法与向量 | 经中文词法样例验证后可为 `lexical_terms` 建 GIN；向量索引只针对确认的空间、维度与度量 |

外键引用侧按查询和删除检查需要建索引，不能假设 PostgreSQL 自动为所有外键列创建索引。不为所有 JSON 字段预先建 GIN，也不承诺某个索引在所有规模都更快；通过实际执行计划和固定数据集验证。

列表用确定顺序和键集游标：对局／存档使用 `(created_at, id)`，分支内事件使用 `(snapshot_revision, event_index)`。API 游标绑定对局、分支、角色和查询截止快照，不直接公开内部修订；跨分支历史另按第 8.3 节构造顺序。已有主键、唯一约束或左侧前缀足以覆盖查询时不重复建等价索引。

近似向量检索必须把对局、可见性、审核、发布解析代次、演示标记和向量空间写入同一授权查询；不得先取全库候选再交给客户端或模型过滤。逻辑过滤不保证 HNSW 在物理执行时先过滤再扫描；近似索引可能因过滤返回不足。先验证权限正确的精确检索，再用实际执行计划、召回集和固定空间条件索引评估优化，不通过放宽权限补足数量。

### 7.4 数据完整性的分工

| 不变量 | 数据库负责 | 应用／发布事务负责 |
| --- | --- | --- |
| 同局、同分支及来源归属 | 复合外键、非空、可空列互斥检查 | 读档跨分支例外、同方资格与历史前缀 |
| 当前头和命令唯一提交 | 头外键、幂等唯一约束、行锁 | 版本比较、状态转换、响应不确定时核对原命令 |
| 单位与持有对象不重复 | JSON 顶层类型和格式标识 | 稳定 ID、引用完整、动作互斥、库存及持有守恒 |
| 资料发布完整 | 片段／向量外键、唯一键、维度检查 | 每个必需片段的解析配置一致、索引覆盖、原文可读、审核与权限 |
| 旧执行者不可写回 | 受控事务、条件更新与受影响行数 | 执行世代、代次、租约和当前上下文一起验证 |
| 历史不可漂移 | 不可变表的写入权限及来源外键 | 冻结计划、摘录、解析配置和版本；不以当前元数据重建历史事实 |

不得在 `CHECK` 中查询其他表、依赖当前时间持续判定会话有效，或以函数间接隐藏跨行规则。需要跨表规则时优先采用明确事务与复合外键；只有应用写入路径之外确有写入者时才评审约束触发器，并为其提供真实数据库测试。

### 7.5 删除、不可变与访问边界

默认使用限制删除的关系，不以级联删除清空游戏历史。首版不提供删除对局、手动存档、已用资料或历史结果的产品操作；清理周期、覆盖和保留时间待确认。规则与资料停用影响新选择，不能破坏已存引用。

不可变快照、事件、处理与引用表限制普通应用路径的更新和删除权限；迁移账号与运行账号分开。运行账号对必需表的新增和受控状态更新按模块授予，不把“代码里不更新”视为完整不可变保障。数据库超级用户不在应用权限保证范围内。

更新中的自动存档入口、任务状态、建议生命周期、文件处理状态及当前头指针是明确例外，字段更新必须经服务事务。原始资料实体不得因取消草稿或重建索引而删除；清理失败文件须确认未被可用版本引用。

可变表也要区分可变列与不可变列：规则／场景只能改可用状态，命令不能改原输入及来源，建议不能改原内容，文档不能改原文件摘要、权限作用域和身份，向量空间不能改模型及维度。先通过列级授权和固定写入语句限制；不默认给运行账号整表任意更新能力。索引数据是可重建派生物，但已被引用的片段仍受历史保留要求约束。

Unity 和浏览器不持有数据库凭据；FastAPI 必须按会话生成角色投影。原始 `state_payload`、`input_view`、命令结果和全文片段不能直接作为 API 响应。资料检索先限定 `(scope_game_id IS NULL OR scope_game_id = 当前对局)`，再按 `visibility` 与角色过滤，`shared` 不代表能跨局读取绑定其他局的资料。

行级安全可作为后续防御层，不自动列为本轮新增实现。若启用，运行账号必须核对表所有者及 `BYPASSRLS` 行为，连接池上下文使用事务级设置并测试串用；RLS 只控制行，仍不能替代快照 JSON 的字段投影。

## 8. 时间、版本、并发与读档

### 8.1 状态版本与执行资格

| 版本 | 范围 | 变化条件 |
| --- | --- | --- |
| `control_revision` | 整局 | 头快照、有效分支或运行控制变化；跨读档保持递增 |
| 快照 `revision` | 单分支 | 每次产生新权威快照递增；新分支从零建立首快照 |
| `world_revision` | 单分支 | 影响单位、任务、路线条件、资源、观察、环境和决策依据的领域内容改变时递增 |
| `execution_epoch` | 整局运行控制 | 创建、读档或受控恢复时换新；避免旧分支、旧备份执行器取得写回资格 |
| `claim_generation` | 单后台任务 | 领取、接管或撤销执行资格时递增；解决同一世代内旧工作线程晚到 |

同一仿真步可能有多个事件、确认和暂停修订，不能只用 `simulation_step` 判断是否过期。发布待确认标识、暂停或仅保存等操作若未改变领域依据，不应机械地让刚生成的建议立刻因自身登记失效；采用时由服务端核对分支、依据内容指纹、领域版本及最新规则。任何实际依据变化均需重评估，不能仅因数值版本看起来相近而复用。

各版本的写入和分类由统一服务承担，不允许客户端自行声明“这次不影响依据”。内部完整快照版本不得绕过投影作为对方私有活动明细暴露给模型；本方输入指纹仅基于允许读取的信息。

运行写回通常同时核对分支、执行世代、领域依据指纹与领取代次。不能只用 `world_revision` 代替世代，或每次普通暂停都使所有后台任务失效。跨分支比较版本数值没有意义，新分支可以从零开始；恢复建议必须按新分支重新绑定并校验。

### 8.2 命令事务

短命令建议在 `READ COMMITTED` 下，通过统一写入路径锁定本局 `games` 行完成串行提交；使用 `FOR NO KEY UPDATE` 保护控制字段，外键所依赖的唯一身份不变。该策略的前提是所有权威写入均遵守同一锁协议，不能声称隔离级别本身已避免全部业务竞争。正常顺序如下：

1. 验证会话、角色及请求结构，按原作用域查已有幂等结果；存在时先比摘要并返回投影后的原收据。
2. 开始事务并锁定对局控制行；再次查同键，避免两个首次请求同时通过事务外预检查。
3. 比较有效分支、依据快照、控制版本和执行世代；已失效的新执行明确拒绝，旧成功收据仍可核对。
4. 插入命令并执行或复核领域转换；新快照、事件、人工处理、存档以及需要的后台任务在本事务写入。
5. 更新有效头和控制修订，写入最终命令结果，提交后才向客户端报告成功。

模型请求、文件解析、资源写入和等待人工均不放进持锁事务。高开销候选计算在固定输入上于事务外进行，提交时再次校验。

并发推进只允许一个结果成功提交；同键重试返回已核对结果，不多推进一步。提交后响应丢失可通过原命令查询，不重新执行。

若数据库提交过程连接断开，客户端不能断言成功或失败；服务恢复后核对命令记录。失败的事务不留下半份快照与事件，诊断性失败记录在明确的新事务中写入，不能把诊断记录误当执行事实。

唯一冲突后不能在已失败的事务中继续普通查询。使用明确的 `ON CONFLICT` 流程、保存点或回滚后重新核对原命令；唯一冲突不是另一条命令已成功的证明。诊断写入也使用原作用域和摘要，若已有并发成功记录则读取原结果，不能覆盖为失败。死锁或序列化冲突按原键重试整个事务，不重试已经无法证明未执行的外部副作用。

异步命令返回 `202` 前，须在同一事务提交命令与唯一执行任务；执行器完成时将领域事实、命令终态和任务终态一起提交。崩溃后的 `accepted/running` 由该任务租约和代次恢复，不允许仅凭状态长期挂起或再次创建重复命令。

### 8.3 读档与历史前缀

读档验证存档完整性和版本后，锁定本局，创建新分支及首快照，将原存档游戏内容恢复并保持暂停，同时切换有效头、增加整局控制版本、轮换执行世代，提交读档命令结果。新首快照拥有新标识，不能将旧分支快照直接作为新分支头。冻结终局不借恢复流程改写；已采用计划作为历史与恢复状态保留，待处理建议才建立新的可处理记录。

原始事实前缀通过 `fork_snapshot_id` 追溯，不把父分支在分叉之后的事件加入新分支历史。若分叉来源处于同一步某个较早修订，前缀截止到该修订而非该分钟全部记录。新分支的资源、损失和持有事实从快照恢复，不重放扣分事件。

多级分叉需递归计算每一段祖先的截止修订，并按“根历史段 → 后代段 → 当前分支修订 → 事件序号”拼接；不能对所有分支的局部 `revision` 直接全局排序，也不能仅处理一层父分支。查询先冻结所读分支和截止头，后续翻页维持同一边界，父分支后写入不改变该历史视图。

待处理建议在新分支建立恢复记录并保留来源，已处理建议作为已发生事实保留；旧工作流与运行中的旧任务不自动获得新分支执行资格。仍需分析时创建或核对新分支运行，不复用另一分支的检查点游标直接提交。

已结束记录与当前进行中分支的访问边界分别检查，不能因为数据库里存在某个已结束分支就公开当前进行中双方私有状态。多分支胜负展示仍待设计，本阶段不新增排行榜或多次尝试取最好成绩的规则。

### 8.4 后台领取与检查点

通过短事务按 `(available_at, created_at, id)` 领取可运行任务，可使用 `FOR UPDATE SKIP LOCKED`；更新归属、租约、执行次数和领取代次后释放事务。`SKIP LOCKED` 只用于任务竞争，不用于读取一致游戏状态。模型或解析在事务外执行，等待人工转为 `waiting_human` 并清除租约，不让队列无限重复领取。

续租只能由匹配任务 ID、`running` 状态、归属、领取代次且尚未过期的执行器完成；已过期执行者不能自行续租复活。到期判断与续租使用数据库时间，避免不同工作进程时钟漂移；短事务可使用 `clock_timestamp()`，不把事务开始时间当持续变化的实时时钟。具体间隔和超时仍待实测。

领取与续租只持有任务行锁，不在持有该锁的事务中继续等待对局行。结果提交统一先锁作用域行（对局或文档版本），再锁命令／任务，随后更新运行和建议；读档及取消也遵守同一顺序。涉及多个同类对象时按稳定 ID 排序，避免某条路径先锁任务再等对局、另一条路径先锁对局再等任务。

恢复不能只把状态改回排队而保留旧代次执行许可。晚到结果可保留为不可执行的诊断，但不能产生新建议采用、单位动作或当前资料发布。

LangGraph 检查点按所选适配器维护，应用用 `ai_runs` 与处理记录对账。图中断前后的副作用需要可幂等或可核对；框架内部表不替代游戏命令、人工确认与完整快照。

检查点写入与游戏事务默认是两个提交边界；即便都使用 PostgreSQL，也不能假设适配器与应用共用同一连接和事务。先持久化游戏收据，再由工作流对账继续；恢复重复进入节点时查询原收据，不能再次扣资源或采用建议。

### 8.5 资料重解析与检索原子发布

1. 锁定 `document_versions`，分配新的 `parse_revision`、递增 `next_parse_revision` 和处理代次，在同一事务登记解析任务；当前已发布清单保持不变。
2. 解析与向量化在事务外计算，以新代次追加片段、冻结配置和向量。未发布的数据不进入查询；大批量写入可分批提交，但不能提前切换活动指针。
3. 发布前锁定文档版本和任务，核对目标处理代次、任务租约、原文件摘要与可读性、审核、片段数量及配置一致性、必要向量空间覆盖。失败仅登记诊断，不替换旧发布。
4. 同一事务更新 `active_parse_revision`、`parser_manifest`、`retrieval_manifest`、`publication_revision` 和可检索状态，标记任务成功。词法与向量查询只使用清单声明的同一解析代次；不能混合新词法与旧向量。
5. 查询在一个 SQL 或只读一致事务内取得发布指针、过滤和候选；长时间重排序完成后返回前再核对权限及发布修订。停用或权限收紧时丢弃已失效候选，缓存按发布修订及授权作用域失效。

清单覆盖检查基于实际选定空间，不将“向量行存在”视为近似索引已经构建成功。小规模精确检索可作为独立有效发布方式；是否必须建近似索引由实际发布策略决定。新版本和新解析不能删除历史证据仍引用的旧片段。

### 8.6 快照存储与查询成本

首版使用完整快照，但只在产生权威状态变化时新建；轮询、相机操作和普通读取不产生快照。仅建立手动存档可引用现有头，不复制相同世界载荷。暂停、建议处理等是否改变快照由统一领域提交规则决定，不能为了减少写入漏记重要事实。

列表和状态摘要只选择必要关系表列，不读取整份 `state_payload`；需要投影时再加载对应头。先测单位数、每局修订数、平均及高分位快照字节、资料与事件规模，记录表／索引大小和恢复耗时。PostgreSQL 自带的变长字段存储能力不等于已解决快照放大；没有测量前不引入分区、差量链、额外缓存或第二套可写状态库。

## 9. 演示数据、迁移与备份

迁移工具待后端依赖方案确定；本轮不引入 Alembic 或其他新依赖。迁移需显式创建应用表、复合约束、必要索引和结构版本。pgvector 扩展由有权部署步骤显式准备，不假设普通应用账号能创建扩展；框架检查点迁移使用正式适配方案，不能手工仿造一张“检查点 JSON 表”替代。

迁移与演示初始化分开。演示命令使用稳定演示键识别规则、场景、资料及对局，重复执行不覆盖用户记录、不重复制造同批样例；正常启动不自动插入对局。缺失地图资源、资料原文或必需参数时报告原因，不创建指向不存在文件的成功记录。

循环关系按建表、添加约束及事务初始化顺序处理，禁止长期关闭外键来导入数据。结构变更先验证迁移与兼容读取，旧快照不就地改写；需要格式转换时生成独立迁移结果和来源关联，具体兼容政策另定。

备份需同时覆盖应用数据、检查点存储、受控原文和资源版本。仅备份 PostgreSQL 元数据不能证明原文可读，仅复制资料目录也不能恢复完整对局。恢复验证应核对快照校验值、头指针、文档引用和会话撤销／重新建立策略，不自动把旧会话凭据作为安全恢复事实。

本机与鲲鹏部署分别验证 PostgreSQL、pgvector、驱动和迁移。OpenHarmony 终端只访问服务接口，不连接数据库。本文未执行任何迁移、备份或实机验证。

### 9.1 实施与回退顺序

| 顺序 | 实施内容 | 独立退出检查 |
| --- | --- | --- |
| 1 | 锁定 PostgreSQL、驱动、Schema 与哈希版本；核心表先不依赖未启用的向量扩展 | 隔离环境能建立最小核心结构，缺可选扩展不冒充检索可用 |
| 2 | 建版本、对局、席位、分支、快照、命令、事件和存档表；建立非延迟唯一目标键 | 字段、非空、状态值及外键目标组合明确 |
| 3 | 补齐循环引用外键和条件索引，配置运行账号的表／列权限 | 同事务建立完整根记录；跨局指针、半空关联和非法修改被拒绝 |
| 4 | AI 与资料阶段建其余十表，并补来源、任务及证据外键；向量扩展显式就绪 | 核心无 AI 时仍可运行合法确定性测试；真实建议和检索单独验收 |
| 5 | 执行命令并发、读档、任务接管和资料发布负例 | DB-01 至 DB-30 及启用的融合用例有真实数据库结果 |
| 6 | 在隔离目标恢复备份，核对原文、资源、检查点与有效头；轮换执行世代 | 旧执行器不能写回，已提交收据和历史引用可核对 |

已存在旧库时先盘点 Schema、迁移版本和归档数据，不把旧版表直接当作本设计；没有批准的映射不自动导入。新增非空列采用明确回填与验证步骤，不能凭默认零或随机值伪造历史关联。无法无损降级时恢复匹配版本的应用及备份，不以删除历史列作为通用回退。

### 9.2 数据库与资源的一致备份

备份清单记录数据库备份标识、Schema／应用版本、规则及场景摘要、被引用原文和资源摘要、检查点位置及备份截止边界。不可变原文先以暂存文件写入、校验并发布受控存储键，再将数据库状态置为可用；失败文件不形成成功引用。数据库事务不能撤销文件系统写入，未引用文件作为待核对残留处理，不影响已发布资源。

检查点、资源与应用表分别存储时，采用短暂停写或明确的共同截止边界并逐项核验；不能把三个独立时间点的副本称为一致备份。密钥单独受控保管，不混入普通导出。恢复完成后先保持暂停，重新建立会话和任务资格，再开放运行。

### 10.1 首版预留范围

### 10.2 数据设计验收情景

以下是实施后的验收要求，本次文档结构检查不等于数据库验证通过。

| 编号 | 场景 | 应观察到的结果 |
| --- | --- | --- |
| DB-01 | 创建本局、三席位、根分支与首快照 | 事务提交后头完整，不能提交悬空或跨局指针 |
| DB-02 | 同一仿真步多次暂停与人工处理 | 修订可区分且排序稳定，不覆盖同一分钟的历史 |
| DB-03 | 同键同输入重试、同键不同输入提交 | 前者返回原结果，后者冲突，不重复推进或触发 |
| DB-04 | 两窗口并发推进或确认 | 版本、锁和唯一约束共同阻止重复结果 |
| DB-05 | 切换到其他局或其他分支的快照／建议 | 复合外键或应用检查拒绝，不靠 UUID 唯一性猜归属 |
| DB-06 | 交接、独立损失后保存并读档 | 同一步恢复，物资不复制、资源不重复恢复、安全分不重复扣 |
| DB-07 | 读档命令成功但响应丢失后重试 | 返回同一个新分支结果，不再建立第二个恢复分支 |

| DB-09 | 读档后旧模型或租约过期执行者返回 | 上下文或代次失效，不写入当前游戏 |
| DB-10 | 仅登记待确认或暂停，领域依据不变 | 服务端核对后建议不会被自身登记机械失效；实际变化仍需重评估 |
| DB-11 | 保存事务失败或数据库提交结果不确定 | 不伪造可恢复记录，能够通过命令与快照核对结果 |
| DB-12 | 失视、通信未知及私有文档检索 | 角色投影不公开隐藏状态，查询前实施资料过滤 |
| DB-13 | 同一建议重复最终处理或非法人工修改 | 唯一处理约束和业务校验阻止重复采用，失败输入不占最终处理记录 |
| DB-14 | 文档换版、重新解析或停用旧资料 | 新查询使用有效版本，历史引用与原文仍可追溯 |
| DB-15 | 向量维度不符或混用不同向量空间 | 外键、维度检查与查询过滤拒绝混用 |
| DB-16 | 当前建议状态改变后读取历史快照 | 历史冻结内容与状态不漂移，复盘不重算模型结果 |
| DB-17 | 重复演示初始化或原文资源缺失 | 不覆盖用户数据，不制造重复或伪成功资源 |
| DB-18 | 从备份恢复并读取对局及引用 | 头、快照、资料和引用完整；平台运行证据单独记录 |
| DB-19 | 同键并发首次提交及失败诊断晚到 | 只保留一个幂等结果，晚到失败不覆盖成功；冲突事务回滚后才能继续核对 |
| DB-20 | 异步命令受理后、任务领取前进程退出 | 已提交命令仍有唯一可领取任务，不丢工作、不创建第二条命令 |
| DB-21 | 同一任务租约到期后旧执行者续租或完成 | 条件更新失败；新代次结果不被覆盖，当前头和发布指针不变 |
| DB-22 | 备份恢复后旧执行器仍携带原世代 | 新世代拒绝旧写回，历史命令仍可查询，普通重启不无故取消所有运行 |
| DB-23 | 连续两次分叉并在祖先同一步追加事件 | 逐段继承截止修订之前的前缀，分页和事件顺序稳定，不混入分叉后的事实 |
| DB-24 | 新解析失败、旧索引仍完整 | 旧活动解析及可用清单保留；无旧发布时不能查询失败的新代次 |
| DB-25 | 旧解析／向量任务在新处理代次发布后完成 | 目标处理代次不符，不能覆盖活动解析或混合词法与向量代次 |
| DB-26 | 嵌入声明错误片段摘要、维度或零余弦向量 | 复合外键／维度检查或输入验证拒绝，不能标为已发布 |
| DB-27 | 插入缺半个来源的证据或跨方恢复建议 | 本行互斥检查、同方外键或历史前缀校验拒绝 |
| DB-28 | 重解析期间标题、配置或发布状态变化后读取旧引用 | 冻结摘录和解析配置可追溯；原文下载仍按当前授权检查 |
| DB-29 | 同命令重复保存与不同命令同名保存 | 前者仅一个手动入口，后者按多个独立记录保留，不以名称覆盖 |
| DB-30 | 运行账号修改不可变内容及连接池复用角色 | 非授权列更新被拒绝；若启用 RLS，旧角色上下文不能串入下一事务 |

外键、唯一、条件索引、可延迟约束、事务失败和任务抢占必须在真实 PostgreSQL 上验证，不能只用内存数据库或 ORM 模拟证明。规模测试记录场景、版本、单位数量、快照体积与耗时，再决定存储优化。

## 11. 技术依据

- [PostgreSQL JSON 类型](https://www.postgresql.org/docs/current/datatype-json.html)：支持 JSONB 结构化存储与索引，同时 JSONB 不保留重复键和对象键顺序，故本项目另定结构校验与哈希协议。
- [PostgreSQL 约束](https://www.postgresql.org/docs/current/ddl-constraints.html)：主键、唯一与复合外键用于关联保护；跨行或跨 JSON 集合业务规则不能伪装成本行 CHECK 已完整保证。
- [PostgreSQL 时间类型](https://www.postgresql.org/docs/current/datatype-datetime.html)：TIMESTAMPTZ 表达时间点，写入与显示时区行为需与仿真步分开。
- [PostgreSQL 条件索引](https://www.postgresql.org/docs/current/indexes-partial.html)、[显式锁](https://www.postgresql.org/docs/current/explicit-locking.html)：支持活动任务去重、按状态查询和数据库并发边界，具体方案仍需真实事务验证。
- [PostgreSQL 18 建表与外键](https://www.postgresql.org/docs/18/sql-createtable.html)：外键目标需满足非延迟唯一性要求，可延迟外键与删除行为要分别定义。
- [PostgreSQL 18 事务隔离](https://www.postgresql.org/docs/18/transaction-iso.html)、[队列行锁](https://www.postgresql.org/docs/18/sql-select.html)：用于核对短事务、重复读取与 `SKIP LOCKED` 的适用边界。
- [PostgreSQL 18 字符类型](https://www.postgresql.org/docs/18/datatype-character.html)、[时间函数](https://www.postgresql.org/docs/18/functions-datetime.html)：用于选择摘要类型及区分事务时间与实际时钟。
- [PostgreSQL 行级安全](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)：表所有者与绕过权限需要单独核对，行过滤不代替 JSON 字段投影。
- [pgvector 官方仓库](https://github.com/pgvector/pgvector)：允许可变维度 vector 存储，但索引需针对同维度集合并匹配查询；中文资料、过滤条件和召回质量另行验证。
- [LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)：工作流检查点由适配器维护，其与游戏存档、分支和人工处理记录的关联由本应用负责。

上述依据用于核对技术能力，不构成当前电脑、鲲鹏或 OpenHarmony 上的运行证明。具体数据库与扩展版本在实施阶段锁定。

### 13.1 既有关系如何承接融合

| 融合内容 | 优先承接位置 | 保持的不变量 |

### 13.2 候选实体与字段草案

以下为后续功能的数据职责，名字是讨论用逻辑名称，不是本轮创建的 SQL 表，也不改变原二十表基线。固定场景只需现有版本清单时，不提前建立完整资产管理库。

| 候选实体 | 最小逻辑字段 | 约束及归属 |

| `agent_bindings` | 本局分支、阵营、单位、会话命名空间、授权政策与绑定修订、有效状态 | 单位属于本局本方；同一授权范围不能有相互冲突的活动绑定；读档后重新核对 |
| `model_profiles` | 生成／向量／排序能力、服务与模型标识、配置版本、预算和凭据引用 | 凭据不写普通 JSON、日志或导出；历史运行固定实际配置，配置更新不改旧记录 |
| `analysis_runs` | 独立分析 ID、来源冻结快照、访问方、方法、干预项、模型及规则版本、结果与证据状态 | 来源授权；与主局有效头及恢复分支分开，不产生主局正式事件或胜负 |

组织树、装备模板和身份映射可以由有版本的资产定义承载；是否拆成额外关系表由查询和规模决定。源节点 ID、目标组织节点 ID、模板 ID 与游戏单位 ID 必须可区分。跨版本映射须保留明确来源，复制子树产生新身份，父子展开不得重复实例化；不按名称自动修复断开的装备引用。

### 13.3 完整性、索引与权限

1. 候选实体若实际采用关系表，使用受审阅的主键、同局归属外键、必填检查与必要唯一约束；JSON 内引用仍需领域校验，不能声称普通外键自动验证整个组织树。
2. 场景发布固定映射、模板、导航与表现清单版本；对局快照记录绑定。资源更新不能就地修改正在运行局的单位能力、道路或规则参数。
3. 命令来源、运行、建议、实际执行与事件关联应能定位同局、同方及允许的来源分支。读档命令结果可以位于新分支，不能错误地限制所有关联都在原分支。
4. 只读 API 对事实重新做角色投影；不能直接返回 `request_payload`、`input_view`、数据库结果缓存或全量审计载荷。筛选、总数、游标和诊断也遵守权限。
5. 对导入查询、活动绑定、来源追踪与分析目录的索引由真实查询确定。不能因为候选实体有名称就预建大量索引、向量库或图数据库。
6. 文件缺失、零资源、未知值、不支持格式和证据不可用分别表达；完整性检查不能把遗漏单位当成已损失，也不能补造观察报告。

### 13.4 导入与后台并发事务

| 场景 | 建议提交边界 | 失败与并发处理 |
| --- | --- | --- |
| 资产转换与发布 | 文件暂存及校验完成，再提交发布清单与可用状态 | 数据库不能自动回滚任意文件系统写入；保留诊断和补偿状态，不发布悬空引用 |
| 导入预览 | 保存输入摘要、检查报告和目标依据，不切换游戏头 | 不兼容或冲突返回原因；预览失败不覆盖合法资产与当前局 |
| 导入确认与恢复 | 锁定并复核有效头、调用资格、输入和依赖；整体建立恢复分支、完整快照与命令结果 | 失败保留原局；原请求重试只返回同一已提交结果；成功后暂停 |
| 模型取消或租约失效 | 更新任务资格或代次，再核对晚到结果 | 不能依靠停止线程保证安全；旧执行者即使仍运行也不能提交当前结果 |
| 分析完成 | 只提交分析结果、方法版本和可用证据 | 主局头、仿真步、资源、任务及分数不变；不能复用主局提交服务 |

导入跨库恢复、外部日志兼容及身份重映射政策仍待 D-07、D-09、D-10；未知格式不通过默认值强行加载。导出不包括可复用凭据、内部系统提示和原始私有运行目录；没有随包提供的 DSH 外部日志不得宣称完整模型证据可恢复。

### 14.1 参考范围与现有规则

| 状态 | 本项目适用内容 |

| 已确认，待后端实现 | 道路网移动、二维可飞区检查、视野范围与明确遮挡、路径过程检查、陆兵间确定性抽象交战、保障到达允许位置后服务 |

[Slitherine 官方生存指南](https://brokenarrow_backend.slitherine.com/news/broken-arrows-survival-guide)分别介绍视野、目标获取、建筑保护和保障职责；[官方玩法指南](https://www6.slitherine.com/news/mission-accomplished-how-to-win-in-broken-arrow)介绍高差、林地、城市、废墟与视线的关系。本节只借鉴这些游戏机制的组织方法，不宣称复现其源码、隐藏公式或当前版本全部参数。具体字段与算法是本项目设计建议。

现有边界继续适用：侦察无人机首版不攻击，保障单位不自动获得攻击能力，兵营不参与伤害；每步一分钟、每单位一个主要动作、同一步统一结算，不引入随机命中。天气仍按既定五步延迟处理，不因画面有雾自动缩短视野或禁飞。参考游戏中的驻楼、修复耐久和其他兵种能力不自动加入本项目。

### 14.2 地图数据在现有表中的归属

| 内容 | 保存位置 | 示例内容及不变量 |
| --- | --- | --- |
| 静态地图几何与设施 | `scenario_versions.definition.map` | 坐标、高程来源、地表区、道路、桥梁、水域、遮挡体、设施、部署及任务区域；场景发布后不可变 |
| 地形和交互规则 | `rule_versions.definition.map_policies` | 通行、视线、射线、隐蔽与掩护政策、叠加顺序、精度及取整；均有政策版本 |
| 兵种能力与属性 | `rule_versions.definition.unit_profiles` | 移动类型、观察能力、抽象作用范围、资源消耗与服务能力；不存入地图区域冒充单位属性 |

| 当前地图变化 | `game_snapshots.state_payload.conditions.map_overrides` | 已启用规则产生的道路状态、事件区域、设施可用性及起止步；按稳定对象 ID 覆盖静态初值 |

| 已发生地图影响 | `game_events.payload` 与命令回执 | 引用对象、政策版本、影响前后值和受阻原因；不创建第二套实时伤害或资源表 |

这些 JSON 路径是新增设计草案，需在 D-07 中确定结构后编码。地图分块只服务空间查询，分块数、三角形数和模型精细度不作为规则强度。首版不按树木、三角形或每个高度采样点建立关系行，也不为本节新增 PostGIS 等扩展。

当前 `SandboxMapData` 已有地图身份、范围、显示高度数组、道路节点与宽度、桥面高度、部署区及建筑显示变换；尚无本节定义的兵种地形响应、权威遮挡体、交战掩护和服务接入政策。现有道路静态连通检查与高度插值均不能作为这些机制已经实现的证据。

### 14.3 静态地图的参数字典

所有对象具有稳定 `object_id`，引用的政策必须存在于对局绑定规则版本。几何以本项目局部坐标表达，显示转换和高程基准明确；不能混用屏幕像素、旧业务坐标和米制地图。

| 参数组 | 建议字段 | 影响什么 |
| --- | --- | --- |
| 地图身份与坐标 | `map_id`、`schema_version`、`coordinate_system_id`、`horizontal_unit`、`vertical_unit`、`axis_definition`、`origin`、`playable_boundary`、`display_transform_version` | 距离、范围、选点和存档绑定的共同基础 |
| 规则高程 | `elevation_source_id`、`storage_key`、`sha256`、`sample_spacing`、`vertical_datum`、`interpolation_policy_id`、`no_data_policy_id` | 经批准后用于坡度或视线；记录采样精度与缺失处理，不直接使用显示 LOD |
| 地表区域 | `region_id`、`terrain_type`、`polygon`、`navigation_layer_id`、`movement_policy_id`、`visibility_policy_id`、`cover_policy_id` | 开阔地、林地、农田、城市地面等的规则身份；隐蔽与掩护政策可显式为空表示未启用 |
| 道路节点与路段 | `node_id`、`edge_id`、`from_node_id`、`to_node_id`、`polyline`、`direction_policy`、`surface_type`、`width`、`movement_policy_id`、`initial_availability` | 道路连接、路径长度、允许通过的移动类型与行进成本；长度按固定几何算法计算并校验 |
| 桥梁 | `bridge_id`、`road_edge_ids`、`deck_geometry`、`navigation_layer_id`、`connectors`、`initial_availability` | 跨水道路与桥面定位；桥面、水面及桥下不能因二维重叠被当成同一位置 |
| 河流与水域 | `water_id`、`polygon`、`ground_passage_policy_id`、`airspace_policy_id` | 地面禁止穿越或限定经桥通过；不因为是水面就自动禁止无人机飞越 |
| 建筑与墙体 | `obstacle_id`、`footprint`、`base_elevation`、`top_elevation`、`ground_blocking_policy_id`、`sight_blocking_policy_id`、`fire_blocking_policy_id` | 完整占地、通行阻挡、观察遮挡和直射阻挡；首版不授予驻楼能力 |
| 林地与植被区 | `vegetation_region_id`、`polygon`、`density_class`、`canopy_height`、`visibility_policy_id`、`movement_policy_id` | 用规则区域表达密度、观察及移动影响，不根据可见树模数量即时计算 |
| 部署与出发点 | `deployment_zone_id`、`side`、`polygon`、`buildable_policy_id`、`ground_connector_ids`、`drone_dock_ids` | 兵营完整占地、道路接入和停靠点合法性 |
| 任务与服务设施 | `facility_id`、`facility_type`、`interaction_area`、`approach_connector_ids`、`service_anchor_ids`、`allowed_service_types`、`initial_availability` | 任务要求的可到达范围、合法交接和停靠服务；仓库、机场、加油站外观不自动授予服务能力 |
| 空中规则区 | `air_region_id`、`polygon`、`flight_policy_id`、`initial_availability` | 首版二维整段航线可飞／禁行检查；不因新增高程字段自行启用三维飞行 |

坡度、道路长度、区域边界等可由发布流程计算，但必须记录算法版本并检查来源。缺失高程不能补为零制造平地；缺失通行政策不能默认为允许。建筑的可见战损档位继续属于显示字段，除非另有已启用的规则状态及映射，否则不改变遮挡、通行或掩护。

### 14.4 兵种参数与地形规则如何匹配

不能只保存一个“森林减速值”并对所有兵种统一生效。规则按 `unit_profile_id + movement_class + terrain_type/政策ID` 匹配，再结合道路和当前地图覆盖状态；同类单位引用同一版本模板，实例只保存自身运行状态。

| 兵种属性组 | 建议字段 | 与地图的关联 |
| --- | --- | --- |
| 移动 | `movement_class`、`traversal_mode`、`base_distance_per_step`、`resource_cost_policy_id` | 陆兵／保障沿道路图，无人机沿二维航线；首版不因地形成本配置开放自由越野 |
| 观察 | `sensor_profile_id`、`observation_range`、`observation_geometry_policy_id`、`occlusion_policy_id` | 在允许观察范围内检查规则遮挡；地面观察与空中观察可以引用不同政策 |
| 抽象交战 | `target_eligibility_policy_id`、`effect_range`、`action_interval_steps`、`effect_strength`、`line_of_fire_policy_id` | 先检查首版陆兵对陆兵资格，再检查已确认信息、作用范围、地图阻挡与资源 |
| 地形影响接受方式 | `terrain_response_profile_id` | 指定本单位适用哪些移动、隐蔽或掩护规则；未启用政策不提供隐藏加成 |
| 保障 | `allowed_service_types`、`service_location_policy_id`、`service_range_policy_id`、`inventory_capacity` | 到达合法服务位置后，检查对象、库存和占用；仍一次服务一个对象、占用一步，不自动修复耐久 |

| 交互政策 | 最小配置 | 首版处理／待确认范围 |
| --- | --- | --- |
| 通行 | `allowed_movement_classes`、`requires_road`、`cost_factor`、`resource_factor` | 道路和二维空中合法性已确认；各成本系数待确认。不可通行必须显式表示，不能用极大成本代替 |
| 观察阻挡 | `blocking_mode`、`applicable_sensor_profiles`、`sampling_policy_id` | 明确遮挡已确认；采用二维区域还是规则高程采样须锁定，不直接调用 Unity 相机可见性 |
| 隐蔽 | `concealment_class`、`detection_adjustment_policy_id` | 本轮建议；影响是否发现，不直接减伤。未启用时只执行既有发现规则 |
| 直射阻挡 | `blocking_mode`、`applicable_action_types` | 本轮建议；将观察射线与动作射线分开，避免共享报告使单位隔墙执行直射 |
| 掩护 | `cover_class`、`applicable_target_profiles`、`incoming_effect_policy_id` | 本轮建议；只在合法交战后影响确定性抽象结果。系数与方向性另定，不引入随机概率 |
| 叠加与优先级 | `overlay_priority`、`terrain_selection_policy_id`、`cover_selection_policy_id`、`rounding_policy_id` | 发布前锁定重叠区域如何取值；不能把森林、废墟和建筑系数无界连乘 |

“看不见”“看见但动作路径被挡”“能作用但受掩护影响”必须分别记录。有效共享观察可以提供目标信息，但是否允许执行仍按动作自己的条件检查。高地只通过已启用的规则几何影响观察或路径；不默认附带射程、伤害或发现距离加成。

系数使用有量纲说明的规范十进制字符串。未确定与未启用分别表示：必需参数未知时阻止该政策启用；明确未启用时使用规则版本声明的无附加效果行为，不以 `null` 自动补零或补一。

### 14.5 在当前地图上的效果示例

以下为本项目拟采用的数据关系示例，不是《断箭》的数值公式，也不是当前 Unity 已实现结果。

| 地图位置 | 陆兵 | 侦察无人机 | 保障单位 |
| --- | --- | --- | --- |
| 主干路与路口 | 沿合法道路边移动，移动耗时受路段政策影响 | 道路不决定飞行路线，检查可飞区与能源 | 沿道路到达服务点；路网不连通则不能完成地面交接 |

| 林地区域 | 是否减速、隐蔽或获得掩护分别由已启用政策决定 | 地面减速政策不直接作用于飞行；林冠观察影响另定 | 地面道路与服务规则生效，不自动穿林越野 |
| 丘陵与洼地 | 经批准的规则高程可改变视线结果，不自动加伤害 | 首版二维飞行保留；观察几何按独立政策处理 | 按合法道路及其成本到达，不因显示坡面平滑就判定可通行 |
| 仓储、机场、加油站 | 可作为明确配置的任务／服务对象 | 只有允许的停靠点支持能源服务 | 只有绑定服务能力的设施可交接；装饰设施不产生库存 |

例如，同样两个陆兵在抽象作用范围内，开阔道路上的情况可能通过观察和动作路径检查；其中一个转到规则墙体后，观察可能失效，或者共享观察仍有效但直射路径不成立。具体结果由冻结输入和启用政策确定，不能只比较双方坐标距离。

### 14.6 结算、动态覆盖与解释记录

建议将地图判断纳入统一规则入口，顺序为：

1. 固定本步的场景、规则、单位模板和地图覆盖状态，核对对象资格、已采用方案与主动作占用。
2. 移动使用实际经过的道路／航段检查边界、通行与资源，不只检查终点。多地表路径按分段成本聚合，取整政策固定，避免每个小段重复取整改变结果。
3. 观察使用本方允许信息、观察能力与已启用遮挡政策产生本方报告；隐蔽政策只有启用后才参与。
4. 交战先核对当前有效信息和抽象作用范围，再检查动作路径及已启用掩护；任何必要条件失败不产生成功作用。
5. 同一步双方按统一规则批量形成结果，写入资源、任务、独立损失、观察和地图相关事件，再提交完整快照；不得因先处理某一方获得额外动作。

该顺序为后端执行阶段设计建议，仍需与规则文档的同一步政策锁定。暂不引入移动后免费攻击、按显示帧触发发现或额外仿真分钟。

动态覆盖只允许由既定规则和合法事件产生，包含 `override_id`、`target_object_id`、`policy_id`、`start_step`、`end_step`、`source_event_id` 和明确有效状态。道路关闭等新事件若未在事件白名单启用，不因字段存在就允许主持人触发。天气、损坏、地形外观和道路通行分别建模，不能隐式互相推导。

回执建议保留 `map_object_ids`、`map_policy_version`、`reason_code`、参与判定的可追溯几何／状态引用和合法前后值，例如通行受阻、观察被遮挡、动作路径被挡、服务位置不可达。面向角色的回执重新投影；不能通过路线失败原因、单位被遮挡数量或地图调试字段暴露未知敌军。未确认动态路线条件显示待核验，不把后端隐藏全局信息直接交给候选生成器。

### 14.7 参数验证与实施优先级

发布时至少检查：几何及坐标一致、对象和政策引用完整、道路节点与桥面连接合法、区域重叠政策确定、边界与容差确定、规则高程无缺失伪值。几何包较大时可保存受控键、版本和摘要并校验资源可读；不在每份快照中复制整张静态地图。

| 顺序 | 优先落地 | 验收目的 |
| --- | --- | --- |
| 第一批 | 坐标、道路／桥梁、水域、可飞区、部署及交接点 | 单位沿合法路线移动，不穿水、穿墙或越界 |
| 第二批 | 显式观察遮挡、兵种观察政策与路径过程检查；评审独立动作射线 | 单位发现和交战受地图几何约束，而非只按距离 |
| 第三批 | 经确认的地形移动成本、隐蔽和确定性掩护 | 同兵种在不同地形呈现可解释差异，不扩充未授权动作 |
| 后续 | 驻楼、越野、动态破坏、烟幕及飞行高度层 | 单独设计能力、事件、状态恢复及独立用例 |

| 编号 | 验收情景 | 独立预期 |
| --- | --- | --- |
| DB-MAP-01 | 同一单位从道路、河岸和桥面规划地面路径 | 使用合法拓扑与导航层，不能直接穿水或桥面跳层 |
| DB-MAP-02 | 途经点合法但航段穿过禁飞区 | 整段检查拒绝，不因终点合法而通过 |
| DB-MAP-03 | 目标在观察范围内但被已配置墙体遮挡 | 不产生当前可见报告，最后发现记录不更新为实时位置 |
| DB-MAP-04 | 友军提供当前信息，但执行者的直射路径被挡 | 在启用直射政策的用例中拒绝该动作，不把共享信息等同动作合法 |
| DB-MAP-05 | 同一地表分别作用于陆兵、无人机和保障单位 | 按各自移动与观察政策匹配，地面减速不自动作用于飞行 |
| DB-MAP-06 | 相同合法交战分别处于无掩护和已启用掩护区域 | 结果遵守冻结规则且确定可重现，未启用政策不产生加成 |
| DB-MAP-07 | 显示树木密度、战损模型、LOD 或相机变化 | 权威路径、发现和交战结果不变；修改规则几何必须发布新版本 |
| DB-MAP-08 | 保存时存在地图覆盖状态，随后恢复或分叉 | 恢复相同对象与有效步区间，不重复执行事件或混用最新地图 |
| DB-MAP-09 | 设施与单位相近但缺少合法接入／交接位置 | 不能仅凭欧氏距离完成服务，不凭加油站模型恢复资源 |
| DB-MAP-10 | 高程缺失、政策缺失、区域重叠不明确 | 阻止相关规则场景发布，不以默认平地或默认可通行补齐 |

本节用例是新增设计要求，尚未执行；不改变 DB-01 至 DB-30 及 DB-MERGE 的既有编号。第三批及后续机制在批准规则与参数前保持未启用，不能据本节宣称当前地图已经影响正式交战结算。
