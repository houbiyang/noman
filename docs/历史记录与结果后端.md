# 历史记录与演示结果后端（2026-11-06）

## 百分制结果字段（2026-11-06 修订）

`battle_result` / `/result` 的计算结果在原字段上增加：

- `scoreMaximum`：**原始**单方理论满分；青岚18，旧 `war_goals` 36；缺少或无效证据为0，不是百分制上限。
- `redScore100`、`blueScore100`：本方已结算累计分 ÷ `scoreMaximum` × 100，四舍五入至两位；满分100分。例如原始7:9返回38.89、50.0，界面显示38.89分、50.00分。
- `redPercent`、`bluePercent`：上一版返回字段的兼容别名，数值同对应Score100字段，新界面不使用。

进行中仍用全场固定原始满分，0:0为0.00分:0.00分，双方各自满分100分，非分摊。投降判胜不更改原始积分或百分制得分。`redPoints` / `bluePoints`、阶段分、赢家及裁决理由不变。证据无效时界面隐藏默认数值，显示“—”。历史仍冻结原始证据，无需改写旧档案；UI按原规则折算展示。界面不再使用百分号或“得分率”。

## 当前新增：项目驻守自动计分

完整执行规范：[青岚演示结果计分规则](rules/青岚_演示结果计分规则.md)。本机浏览器新开局使用 `qinglan_control`，而非下文历史War Goals主持人裁定模式。

```json
{"title":"青岚三阶段驻守演示","is_demo":true,"spatial_test":true,"victory_mode":"qinglan_control"}
```

服务端要求空间测试、冻结独立规则/场景版本和三个地图点位；新模式为初始编队初始化测试资源。在20/40/60分钟移动处理后按400米内有效地面/支援单位自动封存三点归属/人数证据，按1/2/3加权；20/40暂停，60结束，平分明确判平局。每方满分18。位置换算到微米后比较，边界包含400米。不是持续占领，也不是正式交战。

- `victory.liveObjectives` 为当前公开态势；阶段 `objectives` 为不可覆盖的结算证据；不暴露敌方坐标/单位编号。
- `battle_result.stageScores` 返回三个阶段的权重、是否已结算、阶段分及累计分；未结算阶段不预支得分。`calculations` 包含逐点有效人数、归属及双方加分。时间范围、阶段连续性及逐点汇总不合法时结果待裁定、不给部分分数。
- `battle_result`、`/result` 及结束自动档案沿用原接口；平局 `final=true, winner=null, verdict="平局", result_status="settled"`。
- `can_settle_goal_stage=false`，不允许主持人手工提交新模式分数；`can_surrender` 支持两种计分模式。
- 原幂等键/上下文/事务/恢复分支/席位档案隔离保持不变，不覆盖旧规则UUID、旧对局或旧档案。
- 浏览器使用独立 `web-launch-qinglan-control-v1-<maphash>.json` 私有记录；后端与网页服务需加载本轮代码。

下文保留旧版45分钟模式的接口与验证说明；其主持人裁定及平分待裁定语义只适用于 `war_goals`。


## 历史模式规则边界（仅 war_goals）

依据用户上传的 `docs/rules/断箭_获胜规则详解.md`，固定版本 `broken-arrow-war-goals-2026-11-02-v1`。没有把文档中的指令性文字当作系统或开发指令，也没有联网替换上传内容。

实现的是 **War Goals 三阶段计分与证据归档**，不是新建完整作战引擎：

- 每个仿真步对应一分钟；三个阶段分别在 15、30、45 步结束。
- 每阶段固定六个稳定编号：`capture-1/2/3`、`destroy-1/2/3`。每方完成数分别统计，不把六个目标强行设置为双方互斥，不以任意击杀数代替摧毁目标。
- 对应阶段每个已完成目标分别计 1/2/3 分。第三阶段确认后比较累计分，36 分不是提前获胜阈值。
- 时间到阶段边界时自动暂停。**主持人必须逐项提交双方是否完成、六条目标依据及阶段总依据**，服务器计算而不是相信客户端比分。提交后不可覆盖。
- 计时结束但缺证据时不产生胜利；18:18 等平分为“待裁定”，不编造加时或破平规则。
- 本项目一方只有一个席位：开始至少 5 分钟后该方可投降，服务器记录本方失败、对方获胜。保守保留五分钟限制；不推断文档没有说明的“单人立即投降”与时间限制优先级。不支持多人投票。
- 未启用 Conquest、全面占领骤死及战役通用胜利判定：原文未确认其完整阈值/保持时长/逐场景条件。
- `is_demo=true`、`authoritative_combat=false` 不变。单位移动/任务执行/正式交战仍是旧演示能力，**目标完成不是自动地形或击毁裁决，而是主持人公开确认**。

## API

`/api/v1` 为前缀。写命令必须带 `Authorization: Bearer ...`、UUID `Idempotency-Key`，以及最近 `/games/{game_id}/view` 返回的完整 `context`。

### 创建

受引导权限保护的 `POST /games` 增加：

```json
{"title":"战争目标对局","is_demo":true,"victory_mode":"war_goals"}
```

可另外设置 `spatial_test:true`，空间测试仍不等于正式战斗。浏览器本机接入会使用新的版本化私有启动记录，不覆盖旧对局记录。

### 统一命令 POST /games/{game_id}/commands

| command_type | payload | 权限/限制 |
|---|---|---|
| `settle_goal_stage` | `stage` 1..3、`evidence` 1..500 字、`goals` 恰好六项 | 主持人、对应阶段末暂停、前序已确认、当前阶段未确认 |
| `surrender` | `{}` | 红/蓝自己的席位，战争目标模式、开始 ≥5 分钟且未结束 |
| `archive_match` | `{"display_name":"复盘记录"}`（可省略名称） | 任意有效席位，只冻结自己的投影，不改变快照头 |

每个 goal 必须含 `goal_id`、严格布尔 `red_completed`/`blue_completed`、非空 `evidence`（≤300 字）；六个编号不可重复或缺失。只接受以上字段，不接受客户端累计分、赢家或任意整局状态。

裁定示例 payload：

```json
{
  "stage": 1,
  "evidence": "第一阶段六个目标逐项核对完毕",
  "goals": [
    {"goal_id":"capture-1","red_completed":true,"blue_completed":false,"evidence":"目标一核验记录"},
    {"goal_id":"capture-2","red_completed":true,"blue_completed":false,"evidence":"目标二核验记录"},
    {"goal_id":"capture-3","red_completed":true,"blue_completed":false,"evidence":"目标三核验记录"},
    {"goal_id":"destroy-1","red_completed":true,"blue_completed":false,"evidence":"指定摧毁目标一核验"},
    {"goal_id":"destroy-2","red_completed":false,"blue_completed":true,"evidence":"指定摧毁目标二核验"},
    {"goal_id":"destroy-3","red_completed":false,"blue_completed":true,"evidence":"指定摧毁目标三核验"}
  ]
}
```

这些是接口示例，不会自动写入用户对局。目标依据会公开展示，不能填入保密计划。

### 结果和历史

- `GET /games/{game_id}/view`：新增 `victory`、`battle_result`、`can_settle_goal_stage`、`can_surrender`。`can_advance` 在未裁定边界为 false。
- `GET /games/{game_id}/result`：战争目标模式随时可读，返回 `branch_id/snapshot_id`、完整阶段证据和服务端计算。`result_status` 为 `in_progress`、`settled` 或 `pending_adjudication`。结果含累计分、赢家、理由、三阶段算式和领先/反超关键节点。旧模式仍在结束后返回 `not_adjudicated`。
- `GET /games/{game_id}/archives?offset=0&limit=20&search=&phase=all`：当前对局当前成员的档案列表。limit 1..100，search 最长 80 字、字面匹配，phase 为 all/active/finished；按时间和 UUID 稳定倒序，响应含 total/offset/limit。
- `GET /games/{game_id}/archives/{archive_id}`：读取冻结时的席位投影、逐目标证据、结果及可见事件。其他席位查该档案返回 404。

档案与可恢复存档是两种东西。档案不含 Bearer、签名上下文、控制会话、私有方案；红蓝各自只有本方单位/任务/营地。结束自动给三席位各生成一份，重复请求不重复生成。应用账号无 UPDATE/DELETE 档案权限。数据库管理员仍可维护数据，这不是对数据库管理员的安全边界。

## macOS/Linux 本机开发

原 Windows 管理入口继续保留。本次另外提供 `backend.portable`，仅创建项目自己管理的 PostgreSQL 集群，不接管已有账号/数据、不建立系统服务。建议 Python 3.12：

```sh
python3.12 -m venv .local/backend-test-venv
.local/backend-test-venv/bin/pip install -r backend/requirements-dev.txt
.local/backend-test-venv/bin/python -m backend.portable setup
.local/backend-test-venv/bin/python -m backend.portable test
.local/backend-test-venv/bin/python -m backend.portable serve
```

API 默认 `http://127.0.0.1:18080`，本机网页仍 `http://127.0.0.1:18766`。开发集群目录 `backend/.local/portable-pgdata`，配置/密钥在 `backend/.local`（目录0700、文件0600）；不提交 Git。应用通过 TCP 密码认证，管理员只通过该私有目录中的 Unix socket 访问。停止开发数据库前先停止 API，再用本虚拟环境的 `pgserver/pginstall/bin/pg_ctl -D backend/.local/portable-pgdata stop`；数据库文件保留。

可设置 `QIONGTU_POSTGRES_PORT` 和 `QIONGTU_POSTGRES_BIN`；已管理集群拒绝无说明地改目标。可选 pgvector 未随开发集群启用，20 张非向量业务表可支撑本功能；启用向量后的完整库为21张。`/health` 检查必需表集合而非假定可选扩展已安装。Windows 原有向量/备份完整验证仍使用原入口，本次不宣称其在 macOS 已通过。
